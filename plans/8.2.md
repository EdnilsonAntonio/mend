# Plan: 8.2 — Close the repeated `.env`-not-loaded failure mode

## Goal

After this task, no command in the Quickstart requires `set -a && source .env && set +a`
first. Every root npm script that runs `tsx` loads the repository `.env` itself through a
new zero-dependency wrapper (`scripts/with-env.mjs`); the dashboard loads its own
`dashboard/.env.local` through Next.js's native env-file loading; and a committed `.envrc`
plus a rewritten README Setup section make `direnv` the recommended, first-class path, with
the manual `source` command kept as an explicitly-labelled fallback. One precedence rule
holds everywhere: **a variable already present in the environment always wins; otherwise the
file supplies it.**

### Why this design (the alternatives were considered and rejected)

- **`dotenv-cli` as a devDependency** — rejected. It is a 3rd-party dependency added to a
  deliberately lean root package for ~40 lines of parsing, and its behaviour on a missing
  `.env` is version-dependent. We need a guaranteed "missing `.env` is not an error" and a
  guaranteed "never override an existing variable"; owning 40 lines buys both, tested.
- **Node's `--env-file=` flag** — rejected. `--env-file` is not permitted inside
  `NODE_OPTIONS`, `--env-file-if-exists` only exists on Node ≥ 20.12, `package.json`
  declares `engines.node >= 18.17.0`, and whether `tsx` forwards the flag to Node is version
  dependent. Too many ways to be silently wrong on a stranger's machine — which is the exact
  defect class this phase exists to remove.
- **Wrapping `dashboard:dev` with the same wrapper** — rejected. The acceptance criterion
  requires the dashboard to use Next.js's *native* `.env.local` loading, and injecting root
  `.env` into the Next process would make root `.env` silently outrank
  `dashboard/.env.local` (Next never overwrites an already-set variable). One env source per
  app, one precedence rule.
- **Symlinking `dashboard/.env.local` → `../.env`** — rejected. It is not portable, it is
  invisible in `git status`, and it would push `OPENAI_API_KEY` into the dashboard process,
  which has no business holding it.

### Verified facts this plan depends on

1. `dashboard/node_modules/@next/env/dist/index.js` loads, in order,
   `.env.<NODE_ENV>.local`, `.env.local`, `.env.<NODE_ENV>`, `.env` **from the Next project
   directory**, and applies a parsed key only
   `if (typeof u[t]==="undefined" && typeof p[t]==="undefined")`, where `p` is a snapshot of
   the original `process.env`. So `.env.local` works natively and **never overrides** a
   variable already exported by the shell or `direnv`.
2. `npm --prefix dashboard run dev` runs `next dev` with `dashboard/` as the working
   directory — which is precisely why the dashboard does not see the root `.env` today, and
   why `dashboard/.env.local` will be picked up with no code change to `dashboard/lib/db.ts`.
   `dashboard/lib/db.ts` is **not** bypassing Next's loading; it reads `process.env.DATABASE_URL`
   correctly. The only thing missing is a file for Next to read.
3. `.gitignore` line 8 (`.env.*`) matches the basename `.env.local.example`, and the
   existing negation `!.env.example` does **not** rescue it. A second negation is required or
   the new example file will be silently untracked.
4. `resolveGitHubConfig` treats an empty/whitespace `GITHUB_TOKEN` as "not configured"
   (`runner/__tests__/github-pr.spec.ts:183-186`), so the empty `GITHUB_TOKEN=` line in
   `.env.example` is safe to load.

## Implementation steps

### Step 1 — `scripts/with-env.mjs` (CREATE)

The `scripts/` directory does not exist yet; create it. Write the file exactly as below.
No exports: this is a CLI, and the tests drive it as a child process.

````js
#!/usr/bin/env node
// Loads the repository's .env into process.env, then runs the command passed to it.
//
// Used by every root npm script that runs `tsx`, so that `npm run db:migrate`,
// `npm run heal`, etc. work in a freshly opened terminal without a manual
// `source .env` step. See README.md § Setup.
//
// Rules, deliberately boring:
//   * A variable already present in the environment is never overwritten.
//     Your shell (or direnv) always wins over the file.
//   * A missing .env is not an error — the command still runs, and whatever
//     reads the variable reports its own loud error (see db/cli/migrate.cli.ts).
//   * The child's exit code is this process's exit code.
//
// Env file path: $MEND_ENV_FILE if set (resolved against the repo root),
// otherwise <repo root>/.env. Set MEND_ENV_DEBUG=1 to see what was loaded.

import { spawn } from 'node:child_process';
import { readFileSync } from 'node:fs';
import { dirname, resolve } from 'node:path';
import { fileURLToPath } from 'node:url';

const REPO_ROOT = resolve(dirname(fileURLToPath(import.meta.url)), '..');
const KEY_PATTERN = /^[A-Za-z_][A-Za-z0-9_]*$/;

/**
 * Minimal dotenv parser: `KEY=value`, optional `export ` prefix, `#` comments,
 * single or double quotes. Splits on the FIRST `=` so connection strings
 * containing `?sslmode=require` survive intact.
 *
 * @param {string} contents
 * @returns {Record<string, string>}
 */
function parseEnvFile(contents) {
  /** @type {Record<string, string>} */
  const parsed = {};
  for (const rawLine of contents.replace(/^﻿/, '').split(/\r?\n/)) {
    const line = rawLine.trim();
    if (line === '' || line.startsWith('#')) {
      continue;
    }
    const body = line.startsWith('export ') ? line.slice('export '.length).trim() : line;
    const eq = body.indexOf('=');
    if (eq === -1) {
      continue;
    }
    const key = body.slice(0, eq).trim();
    if (!KEY_PATTERN.test(key)) {
      continue;
    }
    let value = body.slice(eq + 1).trim();
    const quote = value.length >= 2 ? value[0] : '';
    if ((quote === '"' || quote === "'") && value.endsWith(quote)) {
      value = value.slice(1, -1);
      if (quote === '"') {
        value = value.replace(/\\n/g, '\n').replace(/\\"/g, '"');
      }
    } else {
      const commentAt = value.search(/\s#/);
      if (commentAt !== -1) {
        value = value.slice(0, commentAt).trimEnd();
      }
    }
    parsed[key] = value;
  }
  return parsed;
}

/**
 * Applies parsed values to `env`, never overwriting an existing variable.
 *
 * @param {Record<string, string>} parsed
 * @param {NodeJS.ProcessEnv} env
 * @returns {number} how many variables were applied
 */
function applyEnv(parsed, env) {
  let applied = 0;
  for (const [key, value] of Object.entries(parsed)) {
    if (env[key] === undefined) {
      env[key] = value;
      applied += 1;
    }
  }
  return applied;
}

function main() {
  const argv = process.argv.slice(2);
  if (argv.length === 0) {
    process.stderr.write('with-env: usage: node scripts/with-env.mjs <command> [args...]\n');
    process.exitCode = 2;
    return;
  }

  const envFilePath = resolve(REPO_ROOT, process.env.MEND_ENV_FILE ?? '.env');
  let loaded = false;
  let applied = 0;
  try {
    const contents = readFileSync(envFilePath, 'utf8');
    loaded = true;
    applied = applyEnv(parseEnvFile(contents), process.env);
  } catch (error) {
    // A missing .env is normal. Anything else is worth saying out loud.
    if (error?.code !== 'ENOENT') {
      const reason = error?.message ?? String(error);
      process.stderr.write(`with-env: could not read ${envFilePath}: ${reason}\n`);
    }
  }
  if (process.env.MEND_ENV_DEBUG === '1') {
    process.stderr.write(
      loaded
        ? `with-env: applied ${applied} variable(s) from ${envFilePath}\n`
        : `with-env: no env file at ${envFilePath}\n`,
    );
  }

  const [command, ...args] = argv;
  const child = spawn(command, args, {
    stdio: 'inherit',
    env: process.env,
    // npm's .bin shims are .cmd files on Windows and cannot be spawned directly.
    shell: process.platform === 'win32',
  });

  for (const signal of ['SIGINT', 'SIGTERM']) {
    process.on(signal, () => {
      child.kill(signal);
    });
  }

  child.on('error', (error) => {
    process.stderr.write(`with-env: failed to run "${command}": ${error.message}\n`);
    process.exitCode = 1;
  });

  child.on('exit', (code, signal) => {
    process.exitCode = signal !== null ? 1 : (code ?? 0);
  });
}

main();
````

Do not add a shebang-based `chmod +x` requirement — the scripts invoke it as
`node scripts/with-env.mjs`.

## Interfaces / types

`scripts/with-env.mjs` — module-private, not exported. Signatures are pinned so the tests
and any future reader agree on behaviour:

````js
/** @param {string} contents @returns {Record<string, string>} */
function parseEnvFile(contents);

/** @param {Record<string, string>} parsed @param {NodeJS.ProcessEnv} env @returns {number} */
function applyEnv(parsed, env);

/** Reads the env file, applies it, spawns argv[2..], mirrors the child's exit code. */
function main();
````

Contract, in words:

| Input | Behaviour |
| --- | --- |
| `KEY=value` | sets `KEY` to `value` |
| `export KEY=value` | same; the `export ` prefix is stripped |
| `KEY="a b"` / `KEY='a b'` | quotes stripped; in double quotes `\n` → newline, `\"` → `"` |
| `KEY=a?b=c&d=e` | value is `a?b=c&d=e` — split on the **first** `=` only |
| `KEY=bare # note` | value is `bare` (unquoted values drop a ` #` trailing comment) |
| `# comment`, blank line, line with no `=`, key failing `/^[A-Za-z_][A-Za-z0-9_]*$/` | skipped |
| `KEY` already in `process.env` | **not** overwritten |
| env file missing (`ENOENT`) | silent; command still runs |
| env file unreadable (any other error) | one-line `with-env:` warning on stderr; command still runs |
| no command argument | `usage` on stderr, exit code `2` |
| child cannot be spawned | one-line `with-env: failed to run "<cmd>"`, exit code `1` |
| child exits with code `N` | wrapper exits `N` |
| child killed by a signal | wrapper exits `1` |
| `MEND_ENV_FILE` set | that path, resolved against the repo root, is read instead of `.env` |
| `MEND_ENV_DEBUG=1` | one `with-env:` line on stderr describing what was applied |

New environment variables introduced by this task (both optional, both read only by the
wrapper): `MEND_ENV_FILE`, `MEND_ENV_DEBUG`.

`scripts/__tests__/with-env.spec.ts`:

````ts
interface WrapperResult {
  readonly code: number | null;
  readonly stdout: string;
  readonly stderr: string;
}

function runWrapper(args: readonly string[], env: NodeJS.ProcessEnv): Promise<WrapperResult>;
````

## Risks

- **`npm --prefix dashboard run dev` might not set the working directory to `dashboard/` on
  some npm versions.** The evidence says it does (that is precisely why the dashboard does
  not see the root `.env` today). Verify with Step 14's `dashboard:dev` check: if Next's
  banner does not mention `.env.local`, **stop and report Blocked** rather than inventing a
  fix — the answer would be to change the root script to an explicit `cd`, and that is a
  design decision, not a Builder decision.
- **Spawning `tsx` by name relies on npm putting `node_modules/.bin` on `PATH`.** True for
  anything run via `npm run`, which is the only way these scripts are invoked. If the
  Builder sees `with-env: failed to run "tsx"`, the cause is running the raw command outside
  npm — use `npm run …`, do not "fix" the wrapper by hardcoding a path.
- **`process.exitCode` instead of `process.exit()` means the wrapper exits only when its
  event loop drains.** With `stdio: 'inherit'` there are no pipes to hold it open, so it
  should exit immediately after the child does. If `npm run db:migrate` visibly hangs after
  printing output, report it as Blocked — do not add `process.exit()` (Task 8.1 removed
  those deliberately, to stop output being truncated).
- **Ctrl-C behaviour.** Adding `SIGINT`/`SIGTERM` listeners removes Node's default
  immediate-exit behaviour for the wrapper. The child receives the signal from the terminal's
  process group anyway; the forwarding is belt-and-braces. Verify Ctrl-C on
  `npm run dashboard:dev` and a long `npm run heal` still returns you to a prompt.
- **Parser subtleties that silently corrupt a connection string.** Splitting on the last `=`,
  or stripping `#` inside a password, would produce a confusing downstream error rather than
  a loud one. Step 5's fixture covers `?sslmode=require&x=1` and a trailing comment for
  exactly this reason — do not weaken those assertions to make a test pass.
- **Duplicated `DATABASE_URL` in two files.** A user who later changes the root `.env` and
  forgets `dashboard/.env.local` gets a dashboard pointed at the old database. This is the
  accepted cost of the acceptance criterion's "dashboard reads its own `.env.local`"; it is
  mitigated by documenting that `direnv` removes the duplication entirely. Do not try to
  solve it with a symlink or a shared loader.
- **`noUncheckedIndexedAccess` is on.** In the spec, `JSON.parse(stdout)` is `any`; index it
  through a typed local (e.g. `const values = JSON.parse(result.stdout) as (string | null)[]`)
  and compare with `expect(values).toEqual([...])` rather than indexing element by element.
- **`noUnusedLocals` is on.** Import only what the spec actually uses from
  `node:fs/promises`.
- **Message coupling with Task 8.3.** `db/cli/migrate.cli.ts`'s `DATABASE_URL is not set`
  wording and the dashboard's `Set DATABASE_URL … then reload.` wording are both quoted in
  Task 8.3's acceptance criteria. The dashboard string changes in the middle only; the
  `DATABASE_URL is not set` message is not touched at all.
