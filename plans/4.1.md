# Plan: 4.1 — Schema and migrations

## Goal

After this task the repository contains a real PostgreSQL schema for `test_runs` and
`heal_attempts` exactly as specified in `DESIGN.md`, expressed as forward-only, versioned,
checksummed SQL migration files, plus a small hand-rolled migration runner (`npm run
db:migrate`, `npm run db:migrate:status`) that applies pending migrations to an empty
database in order, inside a transaction per migration, and records what it applied in a
`schema_migrations` table so a second run is a no-op. Nothing is persisted yet — no runner,
agent, or CLI writes a row (that is Task 4.2). The database-level constraints created here
encode the project's non-negotiable invariants at rest: `pr_url` can only exist on a
`high`-confidence attempt, `status` and `confidence` cannot disagree, a `proposed_selector`
cannot exist without a non-`none` confidence, and `tool_call_count` cannot exceed
`MAX_TOOL_CALLS`.

---

## Read this before you start: the three ways to ruin this task

**1. Writing persistence code.** This task creates the schema and the tool that applies it.
It does **not** insert, update, or select a single application row. There is no repository
layer, no `insertTestRun`, no `recordHealAttempt`. If you find yourself importing
`HealResult` to write it to a table, stop — that is Task 4.2.

**2. Touching `agent/`, `runner/`, `tests/`, or `app-under-test/`.** At the end of this task
`git diff HEAD -- agent/ tests/ app-under-test/ breakage/` must print nothing. The only
permitted link between `db/` and `agent/` is a **type-only** import of `ConfidenceLevel` and
`HealStatus` in `db/schema-contract.ts` (plus the optional cap guard discussed in step 6).

**3. Reaching for an ORM or a migration framework.** No Prisma, no Drizzle, no Kysely, no
`node-pg-migrate`, no `knex`. `DESIGN.md` states the whole point of the hand-rolled OpenAI
loop is that the important machinery stays visible; the same reasoning applies here. Exactly
one new runtime dependency is authorised: `pg`.

## Open questions — answer at the approval gate

These are escalations, not decisions taken unilaterally. **If the human does not answer, the
recommendation stands and the Builder proceeds with it.** Everything below this section
assumes every recommendation is accepted.

### Q1 — Migration tooling and driver (DESIGN.md is silent)

`DESIGN.md` names PostgreSQL and says transcripts are `jsonb`. It does **not** name a driver
or a migration tool, and `TASKS.md` only says "versioned migrations". There is no
`package.json` dependency to inherit from — the project currently has **zero** runtime
dependencies (the OpenAI client is hand-rolled `fetch`).

| Option | What it means | Trade-off |
| --- | --- | --- |
| **A (recommended)** | `pg` (node-postgres) as the only runtime dependency, plus ~180 lines of hand-rolled migration runner over numbered `.sql` files and a `schema_migrations` ledger. | Matches the project's stated ethos exactly: the SQL is the artefact, readable in the diff and in the PR, with nothing generated. `pg` is also what Phase 6's Next.js Server Components will use to read PostgreSQL "directly" per `DESIGN.md`, so it is a dependency the project needs regardless. The runner is small enough to be fully audited. |
| B | Prisma / Drizzle: schema DSL + generated migrations + generated client. | Introduces a code-generation step, a second source of truth for the schema, and a query builder that Phase 6 would then be shaped by. `DESIGN.md` says Server Components read PostgreSQL directly — an ORM is the opposite of that. Also the heaviest possible dependency for two tables. |
| C | `node-pg-migrate`: JS migration files, still needs `pg`. | Same dependency plus one more, and migrations become JavaScript rather than reviewable SQL. Buys us `down` migrations, which v1 does not need. |
| D | Shell out to `psql`. | Zero npm dependencies, but `psql` is not guaranteed installed, gives no structured errors, and Task 4.2 needs `pg` anyway. Rejected. |

Recommendation: **A**.

### Q2 — `finished_at`, `total`, `passed`, `failed` nullability

`DESIGN.md`'s table annotates exactly three columns `(nullable)`: `proposed_selector`,
`failure_reason`, `pr_url`. Read strictly, every other column is `NOT NULL` — including
`test_runs.finished_at`. But Task 4.2 requires that "a crash mid-heal leaves the row in
`investigating`, never silently absent", which only works if the row is inserted when the run
*starts*, at which point `finished_at`, `total`, `passed`, and `failed` are all unknown.

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| **A (recommended)** | `finished_at timestamptz NULL`; `total`/`passed`/`failed` `integer NOT NULL DEFAULT 0`. | Insert-at-start / update-at-end works, an in-flight or crashed run is visibly unfinished (`finished_at IS NULL`), and the counters are never null so the Phase 7 metrics queries need no `COALESCE`. Deviates from the strictest reading of `DESIGN.md` on one column. |
| B | All four `NOT NULL`, row inserted only after the suite finishes. | Literally matches `DESIGN.md`, but a crashed suite leaves no `test_runs` row at all, which contradicts the spirit of 4.2 and of "why store failed attempts". |

Recommendation: **A**. If accepted, record it as a one-line deviation note in `db/README.md`
(step 14) so it is not mistaken for an accident.

### Q3 — `timestamp` vs `timestamptz`

`DESIGN.md` says `timestamp`. The tool is CI-oriented, so run timestamps are compared across
machines and zones.

| Option | Trade-off |
| --- | --- |
| **A (recommended)** `timestamptz` for all four timestamp columns | Correct semantics; `timestamptz` *is* PostgreSQL's timestamp type for anything that crosses a machine boundary. `DESIGN.md` says "timestamp" in a type-sketch table, not a DDL listing. |
| B `timestamp` (without time zone) | Literal match; guarantees a future timezone bug in a CI tool. |

Recommendation: **A**. Note it in `db/README.md` alongside Q2.

### Q4 — `heal_attempts.confidence` on a freshly inserted `investigating` row

`DESIGN.md`'s confidence enum has no "not yet graded" member, but an `investigating` row has
not been graded.

| Option | Trade-off |
| --- | --- |
| **A (recommended)** `confidence heal_confidence NOT NULL DEFAULT 'none'` | `none` already means "no verified fix", which is exactly true of an in-flight or crashed attempt. Keeps the enum matching `DESIGN.md` verbatim and keeps the safety property "only `high` can ever have a `pr_url`" trivially true for in-flight rows. |
| B | Make `confidence` nullable. | Adds a fourth state the confidence gate in `agent/loop/confidence.ts` does not model, and weakens every `CHECK` below. |

Recommendation: **A**.

Decisions **not** escalated, because `DESIGN.md` answers them: the enums are native
PostgreSQL `ENUM` types (the spec says `enum(...)`), and `transcript` is `jsonb`.

## Implementation steps

### 1. Add the dependency

Run `npm install pg` and `npm install --save-dev @types/pg`. Do **not** hand-write version
numbers into `package.json` — let npm resolve them and commit whatever it writes, including
the `package-lock.json` change.

If `npm install` cannot reach the network, **stop and report "Blocked: cannot install `pg`"**.
Do not vendor a driver, do not shell out to `psql`, do not write a PostgreSQL wire-protocol
client.

`pg` is CommonJS. This project is `"type": "module"`. Import it in exactly this form
everywhere, because the named-export form is not reliable under Node ESM:

```ts
import pg from 'pg';
const { Client } = pg;
```

Type-only imports may use the named form: `import type { Client as PgClient } from 'pg';`

### 2. `package.json` scripts

Add these three, keeping the existing ones untouched:

```json
"db:migrate": "tsx db/cli/migrate.cli.ts",
"db:migrate:status": "tsx db/cli/migrate.cli.ts --status",
"test:db": "playwright test --config=playwright.db.config.ts"
```

Add `"playwright.db.config.ts"` and `"db/**/*.ts"` to `include`. Change nothing else — in

### 4. `db/migrations/0001_test_runs.sql`

Write this file verbatim (comments included):

```sql
-- 0001_test_runs
-- One row per Playwright suite execution. Inserted when the run starts, so
-- finished_at is NULL for an in-flight or crashed run. See db/README.md.

CREATE TABLE test_runs (
  id          uuid        NOT NULL DEFAULT gen_random_uuid(),
  started_at  timestamptz NOT NULL DEFAULT now(),
  finished_at timestamptz NULL,
  total       integer     NOT NULL DEFAULT 0,
  passed      integer     NOT NULL DEFAULT 0,
  failed      integer     NOT NULL DEFAULT 0,

  CONSTRAINT test_runs_pkey PRIMARY KEY (id),

  CONSTRAINT test_runs_counts_non_negative
    CHECK (total >= 0 AND passed >= 0 AND failed >= 0),

  CONSTRAINT test_runs_counts_within_total
    CHECK (passed + failed <= total),

  CONSTRAINT test_runs_finished_after_started
    CHECK (finished_at IS NULL OR finished_at >= started_at)
);

CREATE INDEX test_runs_started_at_idx ON test_runs (started_at DESC);
```

`gen_random_uuid()` is built into PostgreSQL 13+; do **not** add `CREATE EXTENSION pgcrypto`
(it needs privileges we should not assume). The runner enforces the version floor in step 7.

### 5. `db/migrations/0002_heal_attempts.sql`

Write this file verbatim:

```sql
-- 0002_heal_attempts
-- One row per heal attempt, including failures. Constraints below encode the
-- project's non-negotiable invariants at rest:
--   * only a high-confidence attempt may ever carry a pr_url
--   * status and confidence can never disagree
--   * a proposed_selector exists if and only if confidence is not 'none'
--   * tool_call_count can never exceed the hard cap of 5

CREATE TYPE heal_confidence AS ENUM ('high', 'low', 'none');
CREATE TYPE heal_status AS ENUM ('investigating', 'healed', 'needs_review', 'failed');

CREATE TABLE heal_attempts (
  id                uuid            NOT NULL DEFAULT gen_random_uuid(),
  test_run_id       uuid            NOT NULL,
  spec_file         text            NOT NULL,
  test_name         text            NOT NULL,
  original_selector text            NOT NULL,
  proposed_selector text            NULL,
  confidence        heal_confidence NOT NULL DEFAULT 'none',
  tool_call_count   integer         NOT NULL DEFAULT 0,
  status            heal_status     NOT NULL DEFAULT 'investigating',
  failure_reason    text            NULL,
  pr_url            text            NULL,
  transcript        jsonb           NOT NULL DEFAULT '{}'::jsonb,
  created_at        timestamptz     NOT NULL DEFAULT now(),

  CONSTRAINT heal_attempts_pkey PRIMARY KEY (id),

  CONSTRAINT heal_attempts_test_run_id_fkey
    FOREIGN KEY (test_run_id) REFERENCES test_runs (id) ON DELETE CASCADE,

  CONSTRAINT heal_attempts_tool_call_count_within_cap
    CHECK (tool_call_count >= 0 AND tool_call_count <= 5),

  CONSTRAINT heal_attempts_status_matches_confidence CHECK (
    (status = 'investigating' AND confidence = 'none')
    OR (status = 'healed' AND confidence = 'high')
    OR (status = 'needs_review' AND confidence = 'low')
    OR (status = 'failed' AND confidence = 'none')
  ),

  CONSTRAINT heal_attempts_selector_requires_verification
    CHECK ((proposed_selector IS NULL) = (confidence = 'none')),

  CONSTRAINT heal_attempts_pr_url_requires_high_confidence
    CHECK (pr_url IS NULL OR confidence = 'high')
);

CREATE INDEX heal_attempts_test_run_id_idx ON heal_attempts (test_run_id);
CREATE INDEX heal_attempts_created_at_idx ON heal_attempts (created_at DESC);
CREATE INDEX heal_attempts_status_idx ON heal_attempts (status);
CREATE INDEX heal_attempts_transcript_gin_idx
  ON heal_attempts USING gin (transcript jsonb_path_ops);
```

The literal `5` in `heal_attempts_tool_call_count_within_cap` is deliberate: SQL cannot import
`MAX_TOOL_CALLS` from `agent/loop/heal-loop.ts`. Do **not** template the SQL to inject it —
migration files must be byte-stable forever, or their checksums drift. Step 6 pins the
relationship instead.

### 6. `db/schema-contract.ts`

The machine-readable statement of what the migrations must produce. Values in `udtName` are
PostgreSQL `information_schema.columns.udt_name` values (`uuid`, `timestamptz`, `int4`,
`text`, `jsonb`, `heal_confidence`, `heal_status`).

Exact contents of the exported values:

- `TEST_RUNS_COLUMNS`: `id`/`uuid`/not-null, `started_at`/`timestamptz`/not-null,
  `finished_at`/`timestamptz`/**nullable**, `total`/`int4`/not-null, `passed`/`int4`/not-null,
  `failed`/`int4`/not-null. In that order.
- `HEAL_ATTEMPTS_COLUMNS`: `id`/`uuid`/not-null, `test_run_id`/`uuid`/not-null,
  `spec_file`/`text`/not-null, `test_name`/`text`/not-null,
  `original_selector`/`text`/not-null, `proposed_selector`/`text`/**nullable**,
  `confidence`/`heal_confidence`/not-null, `tool_call_count`/`int4`/not-null,
  `status`/`heal_status`/not-null, `failure_reason`/`text`/**nullable**,
  `pr_url`/`text`/**nullable**, `transcript`/`jsonb`/not-null,
  `created_at`/`timestamptz`/not-null. In that order — this is `DESIGN.md`'s row order.
- `HEAL_ATTEMPTS_CONSTRAINTS`: the four `CHECK` constraint names from step 5, as a

Include the two compile-time exhaustiveness guards shown in **Interfaces / types** exactly as

If importing `MAX_TOOL_CALLS` as a *value* from `agent/loop/heal-loop.ts` pulls a browser or

naming `MAX_TOOL_CALLS`. Never add an import that runs from `db/` into the agent loop.

### 7. `db/client.ts`

Responsibilities, in this order:

1. `DEFAULT_MIGRATION_SCHEMA = 'public'`, `MIN_POSTGRES_VERSION_NUM = 130000`,
   `MIGRATION_ADVISORY_LOCK_ID = 4104101` (arbitrary but fixed; document it as "task 4.1").
2. `resolveDatabaseUrl(env)` — returns `env.DATABASE_URL` if it is a non-empty trimmed
   string, else `null`. Never throws, never logs the value.
3. `resolveTestDatabaseUrl(env)` — same for `MEND_TEST_DATABASE_URL`.
4. `isValidSchemaName(name)` — `/^[a-z_][a-z0-9_]{0,62}$/.test(name)`. This is the only thing
   standing between a schema name and string-interpolated SQL, so it is not optional.
5. `createDbClient(connectionString)` — returns `new Client({ connectionString })`. No SSL
   configuration, no pool, no retry.
6. `assertSupportedServerVersion(client)` — `SELECT current_setting('server_version_num') AS v`,
   parse to int, throw `MigrationError('unsupported-server-version', ...)` if
   `< MIN_POSTGRES_VERSION_NUM`. Returns the number.
7. `applySearchPath(client, schema)` — throws `MigrationError('invalid-schema-name')` if
   `!isValidSchemaName(schema)`; otherwise runs `CREATE SCHEMA IF NOT EXISTS "<schema>"` then
   `SET search_path TO "<schema>"`.

`MigrationError` is declared in `db/migration-files.ts` (step 8) and imported here.

### 8. `db/migration-files.ts` (pure — no `pg`, no clock, no `process.env`)

1. `MIGRATION_FILE_PATTERN = /^(\d{4})_([a-z0-9_]+)\.sql$/`.
2. `MIGRATIONS_DIR` — resolved relative to the module, **not** to `process.cwd()`:
   `fileURLToPath(new URL('./migrations/', import.meta.url))`. Anything cwd-relative breaks
   when the CLI is invoked from a subdirectory or by Next.js in Phase 6.
3. `class MigrationError extends Error` with `readonly code: MigrationErrorCode` and
   `name = 'MigrationError'`.
4. `computeChecksum(sql)` — `createHash('sha256').update(sql, 'utf8').digest('hex')`.
   No trimming, no newline normalisation: the checksum is of the exact file text.
5. `parseMigrationFileName(fileName)` — returns `{ version, name }` or `null`.
6. `loadMigrationFiles(dir = MIGRATIONS_DIR)` — reads the directory and ignores nothing:
   any entry that is not a file matching `MIGRATION_FILE_PATTERN` throws
   `MigrationError('bad-file-name', ...)`; a repeated version throws
   `MigrationError('duplicate-version', ...)`; returns the files sorted ascending by
   `version` (zero-padded, so plain string sort is correct — do not `parseInt`).
7. `computeMigrationPlan(files, applied)` — pure. Produces `pending` (files whose version is
   not in `applied`, in file order), `checksumMismatches` (files whose version *is* applied
   but whose checksum differs), and `missingFiles` (applied versions with no file on disk).
   Never throws.

### 9. `db/migrate.ts`

`SCHEMA_MIGRATIONS_DDL` (a constant in this file, **not** a migration file — the ledger
bootstraps itself):

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
  version      text        NOT NULL PRIMARY KEY,
  name         text        NOT NULL,
  checksum     text        NOT NULL,
  applied_at   timestamptz NOT NULL DEFAULT now(),
  execution_ms integer     NOT NULL
);
```

`applyMigrations(options)` sequence, exactly:

1. Resolve `schema` (default `DEFAULT_MIGRATION_SCHEMA`) and `connectionString`; throw
   `MigrationError('missing-connection-string')` if the latter is empty.
2. `loadMigrationFiles(options.migrationsDir)` **before** connecting, so a bad filename fails
   without touching the database.
3. Connect. Everything from here to step 10 is inside `try { } finally { await client.end(); }`.
4. `assertSupportedServerVersion(client)`.
5. `applySearchPath(client, schema)`.
6. `SELECT pg_advisory_lock($1)` with `MIGRATION_ADVISORY_LOCK_ID`; release with
   `pg_advisory_unlock` in a nested `finally`.
7. Run `SCHEMA_MIGRATIONS_DDL`.
8. `SELECT version, name, checksum, applied_at FROM schema_migrations ORDER BY version ASC`.
9. `computeMigrationPlan(...)`. If `checksumMismatches` is non-empty, throw
   `MigrationError('checksum-mismatch', ...)` naming every mismatched file — **before**
   applying anything. `missingFiles` is not fatal; carry it into the report.
10. For each pending migration, in order:
    `BEGIN` → `client.query(file.sql)` (one call, multi-statement, **no parameters** — mixing
    parameters with multi-statement SQL silently runs only the first statement) →
    parameterised `INSERT INTO schema_migrations (version, name, checksum, execution_ms)
    VALUES ($1,$2,$3,$4)` → `COMMIT`. On any error: `ROLLBACK`, then rethrow wrapped as
    `MigrationError('sql-error', ...)` with the file name and the original message. Do not
    continue to the next migration. Migrations already committed stay committed — that is
    correct, forward-only behaviour.
11. Return a `MigrateReport`. `pendingAfter` is always `[]` on a successful return.

`getMigrationStatus(options)` does steps 1–9 and returns without applying anything and
without taking the advisory lock. It must not create the schema or the ledger as a side
effect — if either does not exist yet, report every migration as pending (guard the ledger
`SELECT` with `to_regclass('schema_migrations') IS NULL`).

Nothing in this file writes to stdout. Logging is the caller's job via `options.logger`.

## Risks

**`npm install pg` fails (offline / registry blocked).** Stop and report Blocked. Do not
substitute a hand-rolled wire-protocol client, do not shell out to `psql`, do not vendor
`node_modules`.

**`import { Client } from 'pg'` throws at runtime under ESM.** Expected — `pg` is CJS. Use
`import pg from 'pg'; const { Client } = pg;` as specified in step 1. Even if a named import
appears to work in one file, use the default-import form everywhere.

**Multi-statement SQL silently misbehaves.** `client.query(sql)` runs multiple statements only
via the simple query protocol, which is used when **no parameter array is passed**. Passing
`[]` as the second argument switches PostgreSQL to the extended protocol and only the first
statement executes. Never pass a parameter array with a migration file's SQL.

**PostgreSQL < 13 has no built-in `gen_random_uuid()`.** The runner's version guard catches
this with a clear error. Do not "fix" it by adding `CREATE EXTENSION pgcrypto` — report the
version requirement instead.

**Integration tests wipe someone's data.** Mitigated by the throwaway-schema design. If you
cannot make `search_path` isolation work, **stop and report Blocked** — do not fall back to
running the integration tests against `public`, and never write a `DROP DATABASE` or an
unqualified `DROP SCHEMA public CASCADE`.

**The `CHECK` constraints turn out to be too strict for Task 4.2.** They are deliberately
tight because they encode the project's non-negotiable invariants at rest. If 4.2's Builder
hits one, the correct response is to escalate to the Architect, not to write `0003` loosening
the constraint. Specifically: 4.2 must insert `heal_attempts` rows as
`(status='investigating', confidence='none', proposed_selector=NULL, pr_url=NULL)` and then
perform a single terminal `UPDATE` that sets status, confidence, and selector together.

**`schema_migrations` bootstrapping in `getMigrationStatus`.** It must not create the schema
or the ledger as a side effect of a read-only command; use `to_regclass` to detect absence.
A `--status` run against a virgin database must report `applied=0 pending=2` and exit 0, not
error.

**Checksum drift.** Once `0001`/`0002` are applied anywhere, editing them produces a
`checksum-mismatch` error on the next migrate. During this task that is fine (drop the test
schema, or the whole dev database, and re-run). After this task is merged, the rule in
`db/README.md` applies: write a new numbered migration instead.
