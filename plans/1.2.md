# Plan: 1.2 — Write the baseline Playwright suite

## Goal

After this task the repository contains a runnable Playwright test suite in `tests/` —
five spec files, one test each — that passes 5/5 against the pristine `app-under-test/`
via `npm run test:e2e`, and a `playwright.config.ts` that emits machine-readable JSON
results to the fixed, documented path `test-results/results.json`. Each of the five tests
targets exactly one of the five selectors that Task 1.3 will deliberately drift, so that
turning breakage on produces exactly five failing tests with a one-to-one mapping to the
five scenarios. Every test makes at least one real web-first assertion about observable
application state, not merely a click. No application code is touched.

## Architectural decisions already made (do not revisit)

1. **Five spec files, exactly one `test()` per file. No `test.describe()` blocks.**
   Rationale: TASKS.md 1.2 says "five specs" and "5/5 passing"; TASKS.md 1.3 says "exactly
   5 tests fail". One test per file makes that mapping exact. It also means the full test
   title equals the `test()` title (no describe prefix), which Task 2.3's
   `run_single_test` will need in order to select a single test by title, and it means
   "copy the spec file to temp" copies exactly one test's worth of code.

2. **Every drift target is expressed as a single-quoted (or, for the text case,
   double-quoted-inside-single-quoted) string literal passed to `page.locator(...)`, bound
   to a `const`, and appears exactly once in its file.** Rationale: Task 2.3 substitutes
   "only the failing selector" into a temp copy of the spec. That substitution is only
   well-defined if the selector occurs exactly once in the file as a plain literal. Do not
   use `getByRole` / `getByText` / `getByLabel` builders anywhere in this suite — they
   split the selector across an API surface that cannot be replaced by a single string
   swap.

3. **No spec file's `test()` title, and no spec file's *name*, may contain any drift-target
   literal as a substring.** Rationale: same as (2) — a naive textual substitution must not
   be able to corrupt a test title or produce a second match. This is why the files are
   named `cart-add.spec.ts` (not `add-to-cart.spec.ts`) and
   `remember-preference.spec.ts` (not `remember-me.spec.ts`).

4. **No `data-testid` or `data-*` selectors, and no selector that Task 1.3 cannot break.**
   Carried forward from Task 1.1 decision 3. The suite must be breakable by construction.

5. **`retries: 0`, `workers: 1`, `fullyParallel: false`.** Rationale: the healing system
   consumes the JSON results as ground truth. Retries would let a flake masquerade as a
   pass, or produce duplicate result entries the classifier must disambiguate. Serial
   execution of five trivial tests costs nothing and makes result ordering deterministic.

6. **`forbidOnly: true` unconditionally** (not the Playwright default of
   `!!process.env.CI`). Rationale: defence in depth for the project invariant that a test
   must never be made to pass by adding `.only`. Task 2.3 rejects `.only` at the diff
   stage; this makes the runner reject it too.

7. **`outputDir` is `test-results/artifacts`, JSON results go to `test-results/results.json`.**
   Rationale: Playwright wipes `outputDir` at the start of every run. Keeping the JSON
   report one level up from `outputDir` guarantees it is never deleted by a subsequent
   run's cleanup.

8. **`webServer.reuseExistingServer: true`, unconditionally, with no `process.env` read
   anywhere in the config.** Rationale: Task 1.1's server hard-exits on `EADDRINUSE` by
   design, so Playwright must not try to spawn a second one. Reuse is safe because that
   server reads files from disk on every request and sends `Cache-Control: no-store`, so a
   long-lived server still reflects Task 1.3's on-disk breakage toggling. Avoiding
   `process.env` also keeps the config free of a Node-globals dependency at runtime.

9. **TypeScript tooling (`typescript`, `@types/node`, `tsconfig.json`, `npm run typecheck`)
   is introduced now.** Rationale: DESIGN.md mandates "TypeScript (strict)"; this task
   introduces the first `.ts` files in the repository, so this is where strict mode gets
   established rather than retrofitted in Phase 2. `tsc --noEmit` also gives the Reviewer
   an objective check. Playwright transpiles specs itself, so there is still **no build
   step** — `typecheck` is verification only.

10. **Chromium only.** One project, `Desktop Chrome`. Rationale: cross-browser coverage is
    not what this project is demonstrating, and every extra browser multiplies the runtime
    of Phase 3's repeated heal verification runs.

11. **Artifacts off: `trace: 'off'`, `screenshot: 'off'`, `video: 'off'`.** Rationale:
    speed and determinism for the baseline. The dashboard (Phase 6) replays the agent
    transcript, not Playwright traces.

## Implementation steps

1. **Install dependencies** from the repository root:

   ```sh
   npm install --save-dev @playwright/test @types/node typescript
   npx playwright install chromium
   ```

   Record the resolved `@playwright/test` and `typescript` versions in the Verification
   section of the build report. Do not install any other package. Do not install browsers
   other than chromium.

2. **Update `package.json`** so that `scripts` is exactly:

   ```json
   "scripts": {
     "start:app": "node app-under-test/server.mjs",
     "test:e2e": "playwright test",
     "typecheck": "tsc --noEmit"
   }
   ```

   Leave `name`, `version`, `private`, `description`, `license`, and `engines` untouched.
   Do not add a `"type"` field. The `devDependencies` block added by step 1 stays; do not
   add a `dependencies` block.

3. **Append to `.gitignore`** (keep the two existing lines) exactly:

   ```
   test-results/
   playwright-report/
   blob-report/
   ```

4. **Create `tsconfig.json`** at the repository root with exactly this content:

   ```json
   {
     "compilerOptions": {
       "target": "ES2022",
       "module": "ESNext",
       "moduleResolution": "Bundler",
       "lib": ["ES2022", "DOM"],
       "types": ["node"],
       "strict": true,
       "noUncheckedIndexedAccess": true,
       "noUnusedLocals": true,
       "noUnusedParameters": true,
       "esModuleInterop": true,
       "skipLibCheck": true,
       "forceConsistentCasingInFileNames": true,
       "noEmit": true
     },
     "include": ["playwright.config.ts", "tests/**/*.ts"]
   }
   ```

   Do not add `allowJs`. `app-under-test/` must stay outside `include`.

5. **Create `playwright.config.ts`** at the repository root with exactly this content:

   ```ts
   import { defineConfig, devices } from '@playwright/test';

   const APP_BASE_URL = 'http://localhost:3100';
   const JSON_RESULTS_PATH = 'test-results/results.json';

   export default defineConfig({
     testDir: './tests',
     outputDir: './test-results/artifacts',
     fullyParallel: false,
     workers: 1,
     retries: 0,
     forbidOnly: true,
     timeout: 15_000,
     expect: {
       timeout: 5_000,
     },
     reporter: [
       ['list'],
       ['json', { outputFile: JSON_RESULTS_PATH }],
     ],
     use: {
       baseURL: APP_BASE_URL,
       actionTimeout: 5_000,
       navigationTimeout: 10_000,
       trace: 'off',
       screenshot: 'off',
       video: 'off',
     },
     projects: [
       {
         name: 'chromium',
         use: { ...devices['Desktop Chrome'] },
       },
     ],
     webServer: {
       command: 'npm run start:app',
       url: APP_BASE_URL,
       reuseExistingServer: true,
       timeout: 30_000,
       stdout: 'ignore',
       stderr: 'pipe',
     },
   });
   ```

   `JSON_RESULTS_PATH` is deliberately **not** exported — later tasks will define their own
   constant rather than importing a file whose side effect is building a Playwright config.

6. **Create `tests/login-submit.spec.ts`** with exactly this content:

   ```ts
   import { expect, test } from '@playwright/test';

   test('submitting valid credentials updates the login status', async ({ page }) => {
     await page.goto('/');

     const submitButton = page.locator('#login-btn');

     await page.locator('#email').fill('user@example.com');
     await page.locator('#password').fill('hunter2');
     await submitButton.click();

     await expect(page.locator('#login-status')).toHaveText('Signed in as user@example.com');
   });
   ```

7. **Create `tests/cart-add.spec.ts`** with exactly this content:

   ```ts
   import { expect, test } from '@playwright/test';

   test('adding the featured product increments the counter in the nav', async ({ page }) => {
     await page.goto('/');

     const addButton = page.locator('.add-to-cart');

     await expect(page.locator('#cart-count')).toHaveText('0');

     await addButton.click();

     await expect(page.locator('#cart-count')).toHaveText('1');
     await expect(page.locator('#cart-status')).toHaveText('Added Wireless Headphones to cart.');
   });
   ```

8. **Create `tests/product-price.spec.ts`** with exactly this content:

   ```ts
   import { expect, test } from '@playwright/test';

   test('the featured product shows its price directly inside the card', async ({ page }) => {
     await page.goto('/');

     const price = page.locator('#product-card > .product-card__price');

     await expect(price).toBeVisible();
     await expect(price).toHaveText('$149.00');
   });
   ```

9. **Create `tests/login-validation.spec.ts`** with exactly this content:

   ```ts
   import { expect, test } from '@playwright/test';

   test('submitting the form with empty fields shows a validation message', async ({ page }) => {
     await page.goto('/');

     const submitButton = page.locator('button:has-text("Sign In")');

     await expect(submitButton).toBeVisible();
     await submitButton.click();

     await expect(page.locator('#login-status')).toHaveText('Please enter both email and password.');
   });
   ```

10. **Create `tests/remember-preference.spec.ts`** with exactly this content:

    ```ts
    import { expect, test } from '@playwright/test';

    test('the remember preference starts unchecked and can be toggled on', async ({ page }) => {
      await page.goto('/');

      const rememberCheckbox = page.locator('#remember-me');

      await expect(rememberCheckbox).toBeVisible();
      await expect(rememberCheckbox).not.toBeChecked();

      await rememberCheckbox.check();

      await expect(rememberCheckbox).toBeChecked();
    });
    ```

    The leading `toBeVisible()` is load-bearing: when Task 1.3 scenario 5 removes the
    element, this produces an unambiguous "locator resolved to 0 elements" signature as the
    *first* failure, rather than a downstream `.check()` actionability timeout.

11. **Create `tests/README.md`** containing, in this order:
    - One sentence: this is the baseline suite; it must be green against the pristine app,
      and each spec is the designated victim of exactly one Task 1.3 drift scenario.
    - How to run: `npm run test:e2e` (Playwright starts the app itself via `webServer`).
    - A **Spec → drift target → scenario** table with columns
      `Spec file | Drift-target locator | Task 1.3 scenario | Expected failure signature`,
      populated from the "Interfaces / types" section below. The
      `Expected failure signature` column may be left as the short phrases given below;
      exact Playwright error strings are Task 1.3's deliverable, not this task's.
    - A **JSON results contract** section stating that `npm run test:e2e` writes Playwright
      JSON results to `test-results/results.json`, that Playwright artifacts go to
      `test-results/artifacts/`, and that both are gitignored.
    - A **Suite invariants** section listing, as rules for anyone editing these specs:
      one `test()` per file; no `test.describe`; no `.only` / `.skip`; no
      `page.waitForTimeout`; no `getBy*` locator builders; every drift-target selector is a
      single string literal occurring exactly once in its file; no `data-*` selectors.

12. **Verify locally.** The Builder must actually run these from the repository root and
    report the output:

    ```sh
    npm run typecheck                      # exits 0, no output
    npm run test:e2e                       # "5 passed"
    node -e "const r=require('./test-results/results.json'); console.log(r.stats.expected, r.stats.unexpected)"

    npm run test:e2e                       # run a second time; still "5 passed"
    ```

    The second run is not redundant: it proves the suite is idempotent and that

## Interfaces / types

This task introduces no exported TypeScript types. The contracts later tasks depend on are
the following, and they are binding.

**Command contract**

```
npm run test:e2e   ->  playwright test          (5 tests, 5 passing on pristine app)
npm run typecheck  ->  tsc --noEmit             (exit 0)
JSON results path  ->  test-results/results.json
Artifact dir       ->  test-results/artifacts/
Base URL           ->  http://localhost:3100
Browser project    ->  "chromium"
Tool-call-relevant caps: retries=0, workers=1, test timeout 15000ms, expect timeout 5000ms
```

**Spec → drift target → scenario contract**

| Spec file | Drift-target locator literal | Task 1.3 scenario | Expected failure signature when broken |
| --- | --- | --- | --- |
| `tests/login-submit.spec.ts` | `#login-btn` | 1 — renamed `id` | action timeout waiting for `locator('#login-btn')` |
| `tests/cart-add.spec.ts` | `.add-to-cart` | 2 — renamed class | action timeout waiting for `locator('.add-to-cart')` |
| `tests/product-price.spec.ts` | `#product-card > .product-card__price` | 3 — DOM restructure | `toBeVisible` failed, locator resolved to 0 elements |
| `tests/login-validation.spec.ts` | `button:has-text("Sign In")` | 4 — text changed | `toBeVisible` failed, locator resolved to 0 elements |
| `tests/remember-preference.spec.ts` | `#remember-me` | 5 — element removed | `toBeVisible` failed, locator resolved to 0 elements; **no valid replacement exists** |

The two distinct signature shapes (action timeout vs. failed web-first assertion) are
deliberate: Task 3.1's rule-based classifier must handle both.

**Uniqueness contract (enforced by acceptance criteria)**

Each drift-target literal in the table above appears **exactly once across the whole
`tests/` directory**, in its designated file only, and never inside a `test()` title or a
file name.

**Test titles (stable; Task 2.3 may select a single test by title)**

```
submitting valid credentials updates the login status
adding the featured product increments the counter in the nav
the featured product shows its price directly inside the card
submitting the form with empty fields shows a validation message
the remember preference starts unchecked and can be toggled on
```

## Risks

- **`npx playwright install chromium` needs network access and takes a while.** If the
  browser download fails, the suite cannot run and the task is genuinely blocked — report
  **Blocked / unclear** with the download error. Do not work around it by switching to a
  system Chrome channel (`channel: 'chrome'`), which would make the suite depend on the
  developer's machine.

- **Port 3100 occupied by something that is not our app.** With
  `reuseExistingServer: true`, Playwright will happily reuse whatever answers on 3100 and
  every test will fail with confusing selector errors. Before debugging a spec, confirm
  `curl -s http://localhost:3100/ | head -1` returns `<!DOCTYPE html>` and the body matches
  `app-under-test/index.html`. If a foreign process owns 3100, that is an escalation to the
  human, not a config change — 3100 is hard-coded in Task 1.1's server and duplicated in
  this config on purpose.

- **`stats` may be absent from the JSON reporter output on an unexpectedly old Playwright.**
  If `require('./test-results/results.json').stats` is `undefined`, do not restructure the
  reporter config — report the installed version and **Blocked / unclear**. Every
  Playwright 1.30+ release emits `stats`.

- **`outputDir` cleanup deleting the JSON report.** This is precisely why `outputDir` is
  `test-results/artifacts` and the JSON sits at `test-results/results.json`. If the Builder
  "simplifies" these to the same directory, the second consecutive run can delete the
  report and Phase 3 will intermittently read a stale or missing file. Do not merge them.

- **Temptation to use `getByRole` / `getByText`.** Playwright's own documentation
  recommends these, and a Builder trained on that documentation will want to. In this
  project they are wrong: they make the drift target un-substitutable by a single string
  replacement, which breaks Task 2.3. Decision 2 overrides Playwright best practice here.

- **Temptation to add `data-testid` to the app to "stabilise" a selector.** That would make
  the suite unbreakable and silently invalidate Phases 1–3. It is also an edit to
  `app-under-test/`, which is out of scope. Never.

- **Strict-mode violation on `button:has-text("Sign In")`.** This relies on Task 1.1's
  guarantee that the case-insensitive substring "sign in" appears exactly once in the
  rendered body text. If Playwright reports a strict-mode violation here, do not switch to
  `.first()` — that would hide the ambiguity and make the healed selector non-unique.
  Report **Blocked / unclear**; the correct fix would be in the app's copy, which is Task
  1.1's territory.

- **`not.toBeChecked()` on an absent element.** In Task 1.3 scenario 5 this assertion could
  in principle pass vacuously. The preceding `toBeVisible()` in step 10 is what guarantees
  a clean, first-failure selector signature. Do not reorder or remove it as "redundant".

- **Flaky first run because the web server was still booting.** `webServer.url` polling
  handles this; if a timeout occurs, raise nothing — re-run once and report both outcomes.
  Do not add `page.waitForTimeout` or increase `expect.timeout` to paper over it.
