# Plan: 1.3 — Seed the five breakage scenarios

## Goal

After this task the repository can be flipped between a **pristine** and a **broken** state
with a single npm script, deterministically and reversibly, without anyone hand-editing
markup. With breakage on, `npm run test:e2e` produces exactly 5 failing tests — one per
Task 1.3 scenario — with two distinct, documented Playwright error signatures (action
timeout vs. failed web-first assertion) that Task 3.1's rule-based classifier will consume.
Scenario 5 (the removed checkbox) is unfixable **by construction**, not by convention: the
broken DOM contains zero checkbox and zero radio elements, and the affected test calls
`.check()`, which Playwright refuses on any other element type — so no selector exists that
can turn that test green without weakening an assertion. The five `*.spec.ts` files are not
touched by this task at all.

## Open questions — answer at the approval gate

These are escalations, not decisions I have made unilaterally. **If the human does not
answer, the recommendation stands and the Builder proceeds with it.** The plan below is
written assuming every recommendation is accepted.

**Q1 — How does the toggle work?**

| Option | Mechanism | Trade-off |
| --- | --- | --- |
| **A (recommended)** | Two committed full-file variants (`breakage/index.pristine.html`, `breakage/index.broken.html`); the script byte-copies one over `app-under-test/index.html` | Atomic (single `copyFile`, no half-applied state). Restore is exact. Costs one duplicated copy of the markup. |
| B | Script applies forward/reverse string substitutions to `index.html` in place | No duplication, but scenario 5 (deletion) is not invertible without storing the deleted text anyway, and a partially-applied transform after a crash is silent corruption. |
| C | `app-under-test/index.html` becomes generated + gitignored | Removes duplication, but deletes the committed selector contract that Task 1.1's acceptance criteria and `app-under-test/README.md` both refer to. |

Recommendation: **A**. The invariant "the pristine app is recoverable from a committed file
with one command" is worth one duplicated 54-line file.

**Q2 — Where do the documented failure signatures live?**

Recommendation: **canonical verbatim capture in `breakage/README.md`**, mirrored as short
phrases into the existing `Expected failure signature` column of `tests/README.md`, and
also pasted into the Builder's report (which is what TASKS.md literally asks for).
Rejected alternative: a machine-readable `expected-failures.json` fixture — Task 3.1 will
define its own fixture format, and a hand-transcribed JSON here would go stale silently.

**Q3 — Where does the tooling live?**

Recommendation: a new top-level `breakage/` directory. It must **not** live inside
`app-under-test/`, because `server.mjs` serves every file under its own directory — the
broken variant would become fetchable at `/index.broken.html`, polluting the app under
test with artefacts of the harness. `scripts/` is the alternative; `breakage/` is preferred
because it keeps the variants and the CLI that consumes them adjacent.

**Q4 — Scenario 3 requires re-parenting a node inside `#product-card`, a "reserved hook".**

`app-under-test/README.md` currently says reserved hooks "must not be renamed or
restructured". Scenario 3 ("element moved into a wrapper") cannot be implemented on the
price without changing markup inside `#product-card`. The *actual* invariant behind that
rule (plan 1.1, decision 4) is: **drift must never break `app.js`**, because that would
turn seeded selector drift into an application failure — the exact category the system is
required to refuse to heal. Wrapping the price does not break `app.js`
(`productCard.querySelector('button')` is descendant-scoped and still resolves).

Recommendation: **restate the rule precisely** in `app-under-test/README.md` rather than
violate it silently — see Implementation step 7. Reserved hooks keep their ids, and
`#product-card` keeps exactly one `<button>` descendant; non-behavioural descendants may be
re-parented.

## Architectural decisions already made (do not revisit)

1. **The toggle is a byte-exact file copy, never a text transform.** `breakage/apply.mjs`
   uses `fs.copyFile` only. It never parses, rewrites, or regex-substitutes HTML.

2. **State is derived by byte comparison, never stored.** There is no `.breakage-state`
   file, no marker comment in the HTML, no environment variable. State is computed by
   comparing `app-under-test/index.html` against the two variants. A state file can
   disagree with reality; bytes cannot.

3. **`app-under-test/index.html` stays committed in its pristine form.** After
   `npm run break:off`, `git status --porcelain app-under-test/index.html` must be empty.
   Breakage-on is always a dirty working tree, deliberately and visibly.

4. **`break:on` refuses to run from an `unknown` state; `break:off` always restores.**
   `on` must never clobber a file it does not recognise (that could be someone's
   uncommitted work). `off` is the unconditional recovery path and always wins.

5. **`breakage/apply.mjs` is plain ESM JavaScript, not TypeScript.** It mirrors
   `app-under-test/server.mjs`, is harness tooling rather than system code, and must stay
   outside `tsconfig.json`'s `include` array so `npm run typecheck` is unaffected.

6. **`styles.css` is modified once, permanently, to cover both class names.** The drifted
   button class is added alongside the pristine one on the same rules, so the page renders
   identically in both states. Rationale: it keeps the toggle a **single-file** operation
   (only `index.html` changes), which is what makes it atomic. It also mirrors reality —
   a real design-system rename updates the stylesheet.

7. **No `*.spec.ts` file is edited by this task.** Not one character. The suite is the
   fixed contract; breakage happens in the app. This is checkable and is an acceptance
   criterion.

8. **No `data-*` attribute is introduced anywhere**, in either variant. Carried forward
   from Task 1.1 decision 3 and `app-under-test/README.md`.

9. **Drifted names are chosen to have zero substring collision** with any spec filename,
   test title, or other drift-target literal. `#login-btn → #signin-button` and
   `"Sign In" → "Log In"` are mandated by TASKS.md. `.add-to-cart → .purchase-button` is
   chosen (not `.cart-add-*` or `.add-to-*`) so that no future substring-based check can
   confuse the old and new names.

### 3. Create `breakage/apply.mjs`

Zero dependencies. Uses only `node:fs/promises`, `node:path`, `node:url`, `node:process`.
Implement exactly this, with these exact names and exact output strings:

```js
// breakage/apply.mjs
import fs from 'node:fs/promises';
import path from 'node:path';
import process from 'node:process';
import { fileURLToPath } from 'node:url';

const HERE = path.dirname(fileURLToPath(import.meta.url));
const REPO_ROOT = path.resolve(HERE, '..');

const TARGET = path.join(REPO_ROOT, 'app-under-test', 'index.html');
const PRISTINE = path.join(HERE, 'index.pristine.html');
const BROKEN = path.join(HERE, 'index.broken.html');

const USAGE = 'Usage: node breakage/apply.mjs <on|off|status>';
```

Functions (exact signatures):

```js
/** @returns {Promise<'pristine' | 'broken' | 'unknown'>} */
async function readState() { /* … */ }

/** @returns {Promise<void>} */
async function main() { /* … */ }
```

`readState()` behaviour:
- Read all three files as `Buffer`s.
- If `TARGET` is missing, treat it as `'unknown'` (do not throw).
- If `PRISTINE` or `BROKEN` is missing, print to stderr
  `Missing breakage variant file. Expected breakage/index.pristine.html and breakage/index.broken.html.`
  and `process.exit(1)`.
- Return `'pristine'` if `target.equals(pristine)`, else `'broken'` if
  `target.equals(broken)`, else `'unknown'`. Comparison is byte-exact via
  `Buffer.prototype.equals`. Never compare decoded strings, never trim.

`main()` behaviour — command is `process.argv[2]`:

| Command | Current state | Action | stdout / stderr (exact) | Exit |
| --- | --- | --- | --- | --- |
| `status` | any | none | stdout: `pristine` \| `broken` \| `unknown` | `0` |
| `on` | `pristine` | `copyFile(BROKEN, TARGET)` | stdout: `breakage on` | `0` |
| `on` | `broken` | none | stdout: `breakage already on` | `0` |
| `on` | `unknown` | **none** | stderr: `app-under-test/index.html matches neither variant; refusing to overwrite. Run "npm run break:off" to restore the pristine app.` | `1` |
| `off` | any | `copyFile(PRISTINE, TARGET)` unconditionally | stdout: `breakage off` | `0` |
| missing / any other arg | — | none | stderr: the `USAGE` string | `2` |

Each printed message is exactly one line via `console.log` / `console.error` — no banners,
no emoji, no colour, no timestamps.

Prohibited in this file: any npm dependency, `child_process`, `fetch`, network access, any
write to a path other than `TARGET`, any write to `git`, any file deletion, any recursive
directory operation, any `process.env` read.

## Interfaces / types

This task introduces no TypeScript. The following contracts are binding on later tasks.

**Command contract**

```
npm run break:on      -> node breakage/apply.mjs on      -> stdout "breakage on" | "breakage already on"; exit 0
                                                            (exit 1 + stderr if state is unknown)
npm run break:off     -> node breakage/apply.mjs off     -> stdout "breakage off"; exit 0; always restores
npm run break:status  -> node breakage/apply.mjs status  -> stdout one of: pristine | broken | unknown; exit 0
```

Note for the Reviewer: `npm run` echoes the command to stdout. Assert on
`node breakage/apply.mjs status` directly, or use `npm run --silent break:status`.

**Scenario contract**

| # | Scenario | Spec file | Drift-target locator (unchanged) | Markup change | Expected agent outcome |
| --- | --- | --- | --- | --- | --- |
| 1 | renamed `id` | `tests/login-submit.spec.ts` | `#login-btn` | `id="login-btn"` → `id="signin-button"` | healed, high confidence |
| 2 | renamed class | `tests/cart-add.spec.ts` | `.add-to-cart` | `class="add-to-cart"` → `class="purchase-button"` | healed, high confidence |
| 3 | DOM restructure | `tests/product-price.spec.ts` | `#product-card > .product-card__price` | price re-parented into `<div class="product-card__meta">` | healed, likely low confidence |
| 4 | text changed | `tests/login-validation.spec.ts` | `button:has-text("Sign In")` | button text `Sign In` → `Log In` | healed |
| 5 | element removed | `tests/remember-preference.spec.ts` | `#remember-me` | the whole `<label class="field field--inline">` block deleted | **no fix found** — confidence `none`, status `failed`, no PR |

**Failure-signature families** (the shape is binding; the exact string is whatever the
Builder captures from Playwright 1.62 and must be recorded verbatim)

- **Family A — action timeout** (scenarios 1, 2): the failing call is `locator.click()`
  against a locator that resolves to 0 elements. Expected shape:
  ```
  Error: locator.click: Timeout 5000ms exceeded.
  Call log:
    - waiting for locator('#login-btn')
  ```
- **Family B — failed web-first assertion** (scenarios 3, 4, 5): the failing call is
  `expect(locator).toBeVisible()` against a locator that resolves to 0 elements. Expected
  shape includes `expect(locator).toBeVisible()`, the locator string, and an
  element-not-found / timeout indication.

Both families exist on purpose: Task 3.1's rule-based classifier must recognise both as
`selector-drift`, and neither may be classified as `other`.

## Risks

- **The Builder retypes `index.pristine.html` instead of copying it.** A single whitespace
  difference makes `readState()` return `unknown` forever and the toggle unusable. Use
  `cp`, then `cmp`. If `cmp` is not silent, stop and fix before doing anything else.

- **Editor auto-formatting the HTML variants.** Prettier/format-on-save reflowing
  `index.broken.html` will not break anything by itself, but reflowing
  `index.pristine.html` breaks byte-identity with `app-under-test/index.html`. If the
  Builder's environment reformats on write, disable it or verify with `cmp` after every
  write.

- **Committing with breakage on.** This poisons the pristine baseline for every subsequent
  task — Phase 2 and 3 would develop against a broken app and nobody would notice
  immediately. Mitigations: the README warning, the `break:off` recovery path, and the
  acceptance criterion that `git status --porcelain app-under-test/index.html` is empty.
  If the Builder finds `index.html` already dirty at the *start* of the task, that is a
  **Blocked / unclear** report, not something to `git checkout` away.

- **`break:off` clobbering real uncommitted work.** `off` is unconditional by design
  (decision 4). It only ever writes `app-under-test/index.html`, a file that is supposed to
  be pristine-and-committed at rest. This is an accepted trade-off, documented in
  `breakage/README.md`, not a bug to "fix" by adding a confirmation prompt — an interactive
  prompt would make the script unusable from CI.

- **A stale server serving cached HTML after a toggle.** Task 1.1's server reads from disk
  per request and sends `Cache-Control: no-store`, and `playwright.config.ts` sets
  `reuseExistingServer: true` — so toggling while a server is running is safe. If the
  Builder observes the *old* markup after toggling, do not add a cache-buster or restart
  logic: confirm with `curl -s http://localhost:3100/ | grep -c signin-button` first, and
  report **Blocked / unclear** if the server really is serving stale bytes.

- **Fewer or more than 5 failures.** If 4 fail, one drift did not land (most likely the
  price wrapper, if the child combinator still matches). If a test errors during
  `page.goto`, the app is not being served. Diagnose by running a single spec:
  `npx playwright test tests/product-price.spec.ts`. Do **not** "fix" a shortfall by
  editing a spec file.

- **Scenario 3 heals at `high` confidence rather than `low`.** TASKS.md says "likely low
  confidence" — *likely*, not required. `.product-card__price` still resolves to exactly
  one element, so the confidence gate may well score it `high`. That is a correct outcome,
  not a defect, and it is not this task's job to engineer ambiguity into the markup.
  Do not add a second `.product-card__price` element to force low confidence.

- **Temptation to make scenario 5 "a bit fixable".** The single most likely way this task
  is quietly ruined is by leaving a checkbox, a radio, or the text "Remember me" somewhere
  in the broken markup so that a plausible-looking selector exists. Scenario 5 is the proof
  that the agent knows when to stop. If any element remains that `.check()` could act on,
  the task has failed regardless of the other criteria.

- **Playwright error wording differs from this plan's predicted strings.** The strings in
  the Interfaces section are *predictions*, not requirements. The binding artefact is the
  verbatim capture from the installed version. If the wording differs, record what
  Playwright actually printed — do not edit the output to match this document, and do not
  downgrade or pin Playwright to obtain the predicted wording.

- **`npm run break:status` output polluted by npm's own echo.** `npm run` prints the
  command line before executing. Any check that asserts on exact stdout must invoke
  `node breakage/apply.mjs status` directly (or pass `--silent`). Do not "fix" this by
  making the script print extra delimiters.
