# Plan: 3.3 — Extend to all five scenarios

## Goal

After this task the heal loop is exercised against **all five** seeded breakage scenarios, not
just scenario 1, and the repository contains a bounded, repeatable harness that proves it. A
new batch runner heals every entry in the Task 3.1 heal queue sequentially; a new scenario
matrix encodes what each of the five scenarios is *required* to do; and a new CLI
(`npm run heal:all -- --runs=3`) executes the whole queue three consecutive times, checks each
verified fix against an **element-identity oracle** (proving the fix points at the element the
test was written to target, not merely at something that makes the test green), and prints a
PASS/FAIL verdict per scenario. Scenario 5 — the genuinely-removed element — must produce
`proposedSelector === null` in every run; that is the single hardest requirement in this task
and the harness fails loudly if it is ever violated. The model additionally receives the spec
file's source as read-only context so it can recognise when no selector can possibly work. No
confidence scoring, no database, no PR, no dashboard.

---

## Read this before you start: the three ways to ruin this task

**1. Making scenario 5 "a bit fixable."** The correct outcome for
`tests/remember-preference.spec.ts` is `outcome: 'no-fix'`, `proposedSelector: null`. If it ever
comes back `healed`, that is not a win to be celebrated and it is not a flake to be re-rolled —
it means either the breakage was weakened or the verification gate leaked. Report it as
**Blocked / unclear** with the transcript. Do **not** add a special case for scenario 5 anywhere
in `agent/loop/heal-loop.ts`, `prompt.ts`, or `tool-schemas.ts`. The loop stays generic; only
`scenario-matrix.ts` and files under `__tests__/` may name scenarios.

**2. Editing a spec file to make the matrix pass.** `tests/*.spec.ts` is the fixed contract.
`git status --porcelain tests/` must print nothing at the end of this task. If a scenario will
not heal, the answer is a report, never an edit.

**3. Prompt-tuning in a loop until the numbers look good.** The live matrix may be executed at
most **three** times during this build, and a re-run is only permitted after fixing a defect
that the previous report actually identified — never on the hope that the model does better
this time. If three executions do not satisfy the acceptance criteria, that is a
**Blocked / unclear** report with `test-results/heal-matrix.json` attached.

## Open questions — answer at the approval gate

These are escalations, not decisions taken unilaterally. **If the human does not answer, the
recommendation stands and the Builder proceeds with it.** Everything below this section assumes
every recommendation is accepted.

### Q1 — Does the model get to see the spec file's source?

Task 3.2 gave the model the failure context and a DOM snapshot, but not the test it is
repairing. `DESIGN.md` says "Failure context + DOM snapshot" and does not settle whether the
spec source is part of "failure context".

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| **A (recommended)** | The caller reads the spec file and passes it in as `HealDeps.specSource`. The loop embeds it, clamped to 4 000 characters, in the initial user message as explicitly read-only context, and records it in the transcript as `bootstrapSpecSource`. It is **not** a tool call and does not consume the cap. `healFailure` itself does no file I/O — the CLI/queue runner reads the file — so the unit tests stay I/O-free. | Scenario 5 is the case this exists for: the model can see that the test calls `.check()` and asserts `toBeChecked()`, and can conclude in one turn that no selector can fix a missing checkable element. It also sharpens scenarios 3 and 4, where the assertion text identifies the intended element unambiguously. No invariant is weakened: the model still cannot edit the file, still supplies only a selector string, and assertion integrity is enforced by `run_single_test` regardless of what the model has read. There is no cheating vector — a selector that satisfies `toHaveText('$149.00')` *is* the right element. |
| B | Leave the prompt as Task 3.2 left it. | Keeps `prompt.ts` frozen, but the model must infer the test's requirements from a selector and an error string. Scenario 5's "no fix found" then rests entirely on the model noticing the absence of a checkbox in the DOM, which is a weaker guarantee for the task's hardest requirement. |

Recommendation: **A**.

### Q2 — What does "Scenario 3 heals or routes to review" mean before Task 3.4 exists?

TASKS.md 3.3 says scenario 3 must "heal or route to review — never produce a wrong-element
fix." "Routes to review" is `DESIGN.md`'s `low` confidence, which is a Task 3.4 concept and does
not exist yet. Both `high` and `low` require a *verified pass*, so the literal reading is "must
produce a verified fix, of either confidence."

| Option | Encoded as | Trade-off |
| --- | --- | --- |
| **A (recommended)** | Scenario 3's `requiredOutcome` is `'either'` — `healed` and `no-fix` both pass — while the **wrong-element check applies unconditionally**, exactly as it does for scenarios 1, 2 and 4. The binding requirement for scenario 3 in this task is therefore "never a wrong-element fix"; whether it heals `high` or `low` is Task 3.4's problem. | Faithful to the one part of the sentence that is objectively checkable today, and does not invent a confidence gate a task early. If scenario 3 heals (which it is expected to), the harness still verifies the fix points at the price element. |
| B | Require `healed` for scenario 3 too. | Stricter than TASKS.md asks, and would fail the matrix for an outcome TASKS.md explicitly permits. |

Recommendation: **A**.

### Q3 — What is "3 consecutive runs"?

TASKS.md does not say whether that is three runs of each scenario independently or three runs of
the whole queue.

Recommendation: **three consecutive executions of the whole five-scenario heal queue**, in one
`npm run heal:all -- --runs=3` invocation, against one `test-results/results.json` produced by
one broken `npm run test:e2e`. Aggregate PASS requires every scenario verdict in every run to
pass. This is the stricter and more useful reading (it also catches cross-scenario state leakage
such as a temp file or a browser left open).

### Q4 — Where does the harness live, and may it name scenarios?

Plan 3.2 decision 10 forbids scenario literals (`#login-btn`, `login-submit`, …) anywhere in
`agent/loop/*.ts` outside `__tests__/`.

Recommendation: **amend that decision to name exactly one exception**,
`agent/loop/scenario-matrix.ts`, which is the manifest of what the five seeded scenarios must
do. It is harness/evidence code, not loop code. Every other file under `agent/loop/` — including
`heal-loop.ts`, `prompt.ts`, `tool-schemas.ts`, `heal-queue.ts`, and both CLIs — remains free of
scenario literals, and that is an acceptance criterion. Do **not** create `runner/`,
`dashboard/`, or `evidence/`.

## Architectural decisions already made (do not revisit)

1. **The loop stays generic.** No branch, constant, string, or comment in `heal-loop.ts`,
   `prompt.ts`, `tool-schemas.ts`, `openai-client.ts`, `playwright-toolbox.ts`, or
   `heal-queue.ts` refers to a specific scenario, spec file, selector, or element type. The five
   scenarios are data (`scenario-matrix.ts`), never control flow.

2. **The verification gate is untouched.** `verifiedFix` is still assigned in exactly one place
   in `heal-loop.ts`, still guarded by `record.result.passed === true`. This task adds *context*
   for the model and *checks* after the fact; it adds no new way for a fix to be accepted.

3. **`healFailure` performs no file I/O.** The spec source arrives pre-read via
   `HealDeps.specSource`. `agent/loop/__tests__/scenarios.spec.ts` must remain runnable with no
   network, no browser, and no filesystem reads.

4. **The element-identity check is a harness check, not a gate.** It runs *after* a heal, in the
   matrix CLI, and can only turn a PASS into a FAIL in the report. It never feeds back into
   `HealResult`, never causes a retry, and is not part of the confidence rules (Task 3.4).

5. **Sequential only.** Failures are healed one at a time, one browser and one toolbox per
   failure, closed in a `finally`. No parallelism, no worker pool, no queue concurrency. Each
   `run_single_test` already spawns a Playwright child process; overlapping them would make the
   evidence unreliable.

6. **Zero retry logic, still.** A failed heal is a recorded result, not a trigger to try again.
   `--runs` is a bounded repetition count for evidence gathering, hard-capped at
   `MAX_MATRIX_RUNS = 5`, not a retry mechanism.

7. **The per-heal tool-call cap is unchanged at 5** and is not raised, per-scenario or otherwise.
   `MAX_TOOL_CALLS` keeps its single definition in `heal-loop.ts`.

8. **A toolbox that fails to construct yields a synthetic `error` result and the batch
   continues.** One unreachable app or one browser launch failure must not silently truncate the
   evidence to four scenarios.

9. **An `assertHealInvariant` throw aborts the whole batch.** It is defence-in-depth against a
   fix being accepted unverified; it must be loud, not swallowed per-failure.

10. **No new npm dependency.** Node builtins, global `fetch`, and the already-installed
    `@playwright/test` only. `package.json` gains exactly one script and no `dependencies` key.

11. **The matrix report is an artefact, not a committed file.** It is written under
    `test-results/`, which is already gitignored. Committed evidence and metrics are Task 7.1.

12. **Still no confidence, no status, no persistence, no PR.** `HealResult` gains no such fields.

```ts

   * The spec file's source, read by the caller. Read-only context for the model.
   * null when unavailable. `healFailure` never reads the filesystem itself.

```

Making it required is deliberate: it forces every transcript construction site in
`heal-loop.ts` to be updated, and it keeps the shape stable for Task 4.2's `jsonb` column.

### 2. Modify `agent/loop/prompt.ts`

**Add a constant and a helper, both exported:**

```ts
export const MAX_SPEC_SOURCE_CHARS = 4_000;

export function clampSpecSource(text: string): string;
```

`clampSpecSource` is head-clamping and idempotent: returns `text` when
`text.length <= MAX_SPEC_SOURCE_CHARS`, otherwise
`text.slice(0, MAX_SPEC_SOURCE_CHARS) + '\n…[truncated]…'`.

**Append rule 7 to `SYSTEM_PROMPT`**, between rule 6 and the closing "Work efficiently"
paragraph, keeping every existing character of rules 1–6 byte-identical:

```
7. The spec source below is read-only context. You cannot edit it. The only change that will
   ever be applied to it is replacing the one original selector with your candidate. If the
   test's actions or assertions require a kind of element that no longer exists on the page, no
   selector can fix it: answer "no fix found".
```

Rule 7 must contain no scenario literal, no element id, no class name, and no specific
Playwright matcher name.

**Change the signature of `buildInitialMessages`** to take a fourth parameter:

```ts
export function buildInitialMessages(
  failure: ClassifiedFailure,
  appUrl: string,
  snapshot: DomSnapshot,
  specSource: string | null,
): readonly ChatMessage[];
```

The user message layout becomes exactly this, with the spec-source block inserted between the
Playwright error and the DOM snapshot:

```
Spec file: <failure.specFile>
Test name: <failure.testName>
Original selector: <failure.selector ?? ''>
Page URL: <appUrl>
Classifier rule: <failure.rule>

Playwright error:
<failure.errorText>

Current source of the spec file (read-only; you cannot edit it):
<clampSpecSource(specSource)>

Pruned DOM snapshot of the page (captured now, before you start):
<clampHead(snapshot.html, MAX_TOOL_RESULT_CHARS)>
```

When `specSource === null`, the **entire** spec-source block — the heading line, the body, and
the blank line that follows it — is omitted, and the message is byte-identical to the message
Task 3.2 produced. Assert this in a test.

  readonly appUrl: string;

  readonly durationMs: number;

`PlaywrightToolbox` from `playwright-toolbox.ts` already satisfies `ClosableToolbox`
structurally; do **not** modify `playwright-toolbox.ts`.

**`readSpecSourceFromDisk`:**

```ts
export async function readSpecSourceFromDisk(specFile: string): Promise<string | null>;
```

Resolve `specFile` against the repository root computed the same way `run-single-test.ts` does
it (`resolve(dirname(fileURLToPath(import.meta.url)), '..', '..')`). `readFile(path, 'utf8')`,
return `clampSpecSource(source)`. Return `null` on any thrown error. Never throws.

**`healQueueSequentially`:**

```ts
export async function healQueueSequentially(
  failures: readonly ClassifiedFailure[],
  deps: HealQueueDeps,
): Promise<HealQueueResult>;
```

For each `failure`, in input order, with no concurrency:

1. `let specSource: string | null = null; try { specSource = await deps.readSpecSource(failure.specFile); } catch { specSource = null; }`
2. `let toolbox: ClosableToolbox;`
   `try { toolbox = await deps.createToolbox(failure); } catch (error) { results.push(toolboxErrorResult(failure, deps.model.model, message)); continue; }`
3. ```ts
   try {
     results.push(
       await healFailure(failure, {
         model: deps.model,
         toolbox,
         appUrl: deps.appUrl,
         specSource,
         ...(deps.maxToolCalls === undefined ? {} : { maxToolCalls: deps.maxToolCalls }),
       }),
     );
   } finally {
     try { await toolbox.close(); } catch { /* a close failure must not mask a heal result */ }
   }
   ```
   A throw from `healFailure` (only `assertHealInvariant` can do that) propagates out of
   `healQueueSequentially` after the toolbox is closed. That is intentional — see decision 9.

Return `{ startedAt, durationMs: Date.now() - t0, results }` with `startedAt` an ISO 8601 string.

**The element-identity oracle:**

```ts
export type ElementIdentityVerdict =
  | 'same'
  | 'different'
  | 'proposed-not-unique'
  | 'proposed-no-match'
  | 'oracle-unavailable'
  | 'check-error';

export async function checkElementIdentity(
  page: Page,
  proposedSelector: string,
  oracleSelector: string | null,
): Promise<ElementIdentityVerdict>;
```

`Page` is `import type { Page } from '@playwright/test';`. The function never throws. Steps,
in order, inside one `try`/`catch` whose `catch` returns `'check-error'`:

1. If `oracleSelector === null` or `oracleSelector.trim() === ''` → `'oracle-unavailable'`.
2. `const proposedCount = await page.locator(proposedSelector).count();`
   `0` → `'proposed-no-match'`; `> 1` → `'proposed-not-unique'`.
3. `const oracleCount = await page.locator(oracleSelector).count();`
   anything other than `1` → `'oracle-unavailable'`.
4. ```ts
   const handle = await page.locator(oracleSelector).elementHandle();
   if (handle === null) return 'oracle-unavailable';
   try {
     const same = await page
       .locator(proposedSelector)
       .evaluate((el, other) => el === other, handle);
     return same ? 'same' : 'different';
   } finally {
     await handle.dispose();
   }
   ```

**Verdicts:**

```ts
export type ScenarioFailureReason =
  | 'unknown-scenario'
  | 'heal-error'
  | 'expected-healed-but-not'
  | 'expected-no-fix-but-healed'
  | 'wrong-element-fix'
  | 'fix-not-unique'
  | 'identity-check-failed';

export interface ScenarioVerdict {
  readonly scenario: number;
  readonly specFile: string;
  readonly requiredOutcome: RequiredOutcome;
  readonly outcome: HealOutcome;
  readonly stopReason: HealStopReason;
  readonly proposedSelector: string | null;
  readonly toolCallCount: number;
  readonly capReached: boolean;
  readonly durationMs: number;
  /** null when no fix was proposed — there is nothing to check. */
  readonly identity: ElementIdentityVerdict | null;
  readonly pass: boolean;
  /** Empty if and only if `pass` is true. Ordered as evaluated. */
  readonly failureReasons: readonly ScenarioFailureReason[];
}

export function evaluateScenario(
  result: HealResult,
  identity: ElementIdentityVerdict | null,
  expectations?: readonly ScenarioExpectation[],
): ScenarioVerdict;
```

`expectations` defaults to `SCENARIO_EXPECTATIONS`. Logic, in this exact order:

1. `const expectation = expectations.find((e) => e.specFile === result.specFile);`
   If `undefined` → return a verdict with `scenario: 0`, `requiredOutcome: 'either'`,
   `identity`, `pass: false`, `failureReasons: ['unknown-scenario']`, and the remaining fields
   copied from `result`.
2. `const reasons: ScenarioFailureReason[] = [];`
3. If `result.outcome === 'error'` → push `'heal-error'`.
4. If `expectation.requiredOutcome === 'healed'` and `result.outcome !== 'healed'` → push
   `'expected-healed-but-not'`.
5. If `expectation.requiredOutcome === 'no-fix'` and `result.proposedSelector !== null` → push
   `'expected-no-fix-but-healed'`.
6. If `result.proposedSelector !== null`, switch on `identity`:
   - `'same'` → push nothing
   - `'different'` → push `'wrong-element-fix'`
   - `'proposed-not-unique'` → push `'fix-not-unique'`
   - `'proposed-no-match'`, `'oracle-unavailable'`, `'check-error'`, or `null` → push
     `'identity-check-failed'`
7. `pass = reasons.length === 0`.

        model: client,
        appUrl: url,
        createToolbox: (failure) => createPlaywrightToolbox(failure, { appUrl: url }),
        readSpecSource: readSpecSourceFromDisk,
      });
      ```
   c. Identity checks: launch **one** `chromium` browser, one page, `page.goto(url)`. For each
      `result` in `queueResult.results`: if `result.proposedSelector === null` → `identity =
      null`; otherwise look up the expectation by `result.specFile` and call

      Close the browser in a `finally`. If the browser cannot be launched or navigated, record
      `identity = 'check-error'` for every result and continue — do not abort the run.
   d. `const scenarios = queueResult.results.map((r, i) => evaluateScenario(r, identities[i]));`
   e. `runVerdicts.push(evaluateRun(run, runStartedAt, Date.now() - t, scenarios, expectedSpecFiles));`
   f. Print the per-scenario lines for this run as they are produced (step 7 format), so a long
      matrix shows progress.

## Risks

- **Ambiguity (escalated as Q2): "routes to review" has no representation before Task 3.4.**
  This plan encodes scenario 3 as `requiredOutcome: 'either'` plus an unconditional
  wrong-element check. If the human prefers the stricter reading (`healed` required), change
  only `SCENARIO_EXPECTATIONS[2].requiredOutcome` to `'healed'` — no other code changes.

- **Ambiguity (escalated as Q3): "3 consecutive runs" could mean per scenario or per queue.**
  This plan uses three consecutive runs of the whole queue. If the human means something else,
  say so before the Builder starts; it changes the CLI's loop shape.

- **Ambiguity (escalated as Q1): showing the model the spec source is a prompt-contract change
  made in this task, not in Task 3.2.** It is additive and optional (`specSource?`), so every
  existing Task 3.2 test compiles and passes unchanged. If the human rejects Q1, delete steps 1
  (the `HealDeps` field), 2, 3b/3d, and tests 8–13, and keep everything else — but expect
  scenario 5 to be a weaker guarantee.

- **Scenario 5 heals.** If any run returns a non-null `proposedSelector` for
  `tests/remember-preference.spec.ts`, **stop**. Do not adjust the harness, do not re-roll, do
  not add a filter. Capture the full transcript for that attempt (`--json-out` already stores it)
  and report **Blocked / unclear**. Either the broken markup regained a checkable element, or
  `run_single_test` reported `passed: true` for a test that did not really pass — both are
  spec-level alarms.

- **A scenario heals to the wrong element.** The oracle exists precisely to catch this. If
  `identity === 'different'` appears, report it with the proposed selector and the oracle
  selector; do not relax the oracle to make it pass.

- **The oracle selectors are only valid with breakage on.** `#signin-button` and
  `.purchase-button` do not exist in the pristine markup, and `#product-card > .product-card__price`
  does not exist in the broken markup. Running the matrix with breakage off will produce
  `identity: 'oracle-unavailable'` everywhere. The CLI does not detect the breakage state; if
  the verdicts look uniformly wrong, run `npm run break:status` first.

- **Wall-clock cost.** Three runs × five scenarios × up to five tool calls, where each
  `run_single_test` spawns a fresh Playwright child process, will take several minutes. That is
  expected. Do **not** "fix" it with parallelism, a shorter timeout, or a lower cap.

- **`npm run test:tools` run with breakage on.** `agent/loop/__tests__/element-identity.spec.ts`
  is written against state-independent selectors so it is safe either way, but other
  pre-existing tool tests may not be. Always run the offline suite with breakage **off**.

- **Model non-determinism.** Scenarios 1, 2, and 4 are required to heal in all three runs. If one
  run misses, that is a real failure of the acceptance criteria — record it and report, but do
  not re-run the matrix hoping for a better draw. Only re-run after fixing a defect the report
  identified, and never more than three matrix executions in total.

- **`elementHandle()` leaking.** `checkElementIdentity` must `dispose()` the handle in a
  `finally`. Fifteen leaked handles per run across a long matrix will not crash anything, but the
  cleanup is one line and its absence is a review failure.

- **The `HealTranscript.bootstrapSpecSource` field is required, not optional.** That is
  deliberate — it makes the compiler point at all three construction sites in `heal-loop.ts` plus
  the new one in `heal-queue.ts`. If the Builder is tempted to make it optional to silence a type
  error, that is the wrong fix: add the field at the site the compiler is complaining about.

- **`--json-out` writing outside `test-results/`.** The path comes from the command line; the CLI
  must not sanitise or rewrite it, but the documented and verified path is
  `test-results/heal-matrix.json`, which is already gitignored. Do not add the report to git.
