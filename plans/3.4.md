# Plan: 3.4 — Confidence gate

## Goal

After this task, every heal attempt carries a **confidence level** (`high` / `low` / `none`)
and a **status** (`healed` / `needs_review` / `failed`) computed by a pure, deterministic
function from observable signals only — a deterministically measured DOM match count for the
verified selector, the model-initiated tool-call count, and whether a verified pass happened at
all. The model is never asked how sure it is, and no field of `ConfidenceSignals` can carry
model prose. The single boolean `prEligible` (`confidence === 'high'`) becomes the one place any
future PR step is allowed to consult, and `assertPrEligible` refuses anything else, so `none`
provably has no PR path even before Task 5.1 exists. Both existing CLIs report confidence.
No PR is opened, nothing is persisted, and `agent/loop/heal-loop.ts` is not touched.

---

## Read this before you start: the three ways to ruin this task

**1. Asking the model how confident it is.** There is no path in this task where assistant text,
`contentPreview`, `finishReason`, token usage, or any message content influences a confidence
level. `agent/loop/confidence.ts` must never read `HealResult.transcript.messages`,
`HealResult.transcript.modelRequests`, or any `content` field. If you find yourself wanting a
"the model said it was sure" signal, stop — that is the exact thing this task exists to forbid.

**2. Letting confidence change what counts as a fix.** Confidence is computed *after*
`healFailure` returns, from a `HealResult` that is already final. It never re-runs a test, never
retries, never proposes an alternative selector, and never turns a non-verified attempt into a
verified one. In particular, a `low` confidence result still has a real, executed, passing
verified fix — it is routed to a human, not discarded.

**3. Touching `agent/loop/heal-loop.ts`.** The verification gate, the cap, and the single
`verifiedFix` assignment are frozen. `git diff HEAD -- agent/loop/heal-loop.ts` must print
nothing at the end of this task. Same for `agent/loop/types.ts`, `agent/loop/prompt.ts`,
`agent/loop/tool-schemas.ts`, and `agent/loop/scenario-matrix.ts`.

## Open questions — answer at the approval gate

These are escalations, not decisions taken unilaterally. **If the human does not answer, the
recommendation stands and the Builder proceeds with it.** Everything below this section assumes
every recommendation is accepted.

### Q1 — Where does "exactly 1 DOM match" come from?

`DESIGN.md` §4 says `high` requires "verified pass, exactly 1 DOM match, ≤ 2 tool calls". It does
not say where the match count is read from. Two readings exist, and they disagree in practice.

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| **A (recommended)** | After `healFailure` returns with a non-null `proposedSelector`, the **caller** (the queue runner / the `heal:one` CLI, both of which still hold the toolbox open) calls `toolbox.querySelector(proposedSelector)` exactly once and records the result as a `VerifiedFixMeasurement`. That measured `matchCount` is the only match-count input to the gate. | The signal answers the question the gate actually cares about — *is this selector ambiguous?* — rather than *did the model happen to check?* It is always available, deterministic, model-free, and ungameable. It costs one extra browser query per verified heal: no model call, no spend, no effect on `MAX_TOOL_CALLS`, no entry in `transcript.toolCalls`. It also avoids a perverse incentive: under option B, a model that goes straight to `run_single_test` and heals in **one** tool call would be graded *worse* than one that took two. |
| B | Scan `transcript.toolCalls` for the last `query_selector` record whose `selector === proposedSelector`; if there is none, treat the count as unavailable and grade `low`. | Zero new I/O, and it matches the sentence already in `agent/loop/README.md` ("`query_selector` + `run_single_test` = 2 calls"). But the signal is then a side-effect of model behaviour, which is uncomfortably close to "derived from the model", and it penalises efficiency as described above. |

Recommendation: **A**. Note that both options measure against the same idle page and therefore
share the same known limitation (see Risks): a selector for an element that only appears after an
interaction can measure `0`. Under A that yields `low`, which is the correct conservative answer.

### Q2 — Does `heal:all` (the Task 3.3 matrix CLI) report confidence?

Task 3.3 pinned `heal-all.cli.ts`'s stdout format and the JSON shape it emits.

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| **A (recommended)** | **Append-only** changes: each existing per-scenario run line keeps every field it has today, in the same order, byte-identical, and gains ` confidence=… status=… prEligible=… matchCount=…` at the end. One new aggregate line is printed immediately **before** the existing final `matrix …` line. The emitted JSON becomes a strict superset of `MatrixVerdict` with one added key, `confidenceTotals`. | Every Task 3.3 acceptance criterion still holds literally (the `matrix …` line is still the final line; `pass`, `runs`, `runVerdicts` are all still present and unchanged). The confidence gate becomes visible on the one surface that exercises all five scenarios. |
| B | Leave `heal-all.cli.ts` untouched; confidence is only visible via unit tests and `heal:one`. | Smaller diff, but the gate is then never observed against scenario 5 (`none`) and scenario 3 (`low`), which is the most convincing evidence this task can produce. |

Recommendation: **A**.

### Q3 — What does `heal:one --json` print now?

Today it prints a `HealResult`. The natural unit after this task is the assessment, which
*contains* the result.

Recommendation: **`heal:one --json` prints a `HealAssessment`, with the previous payload nested
under `.result`.** Exit codes and the non-`--json` output's existing lines are unchanged. This is
the shape Tasks 4.2 and 5.1 will consume, so pinning it now avoids a second change later.

## Architectural decisions already made (do not revisit)

1. **`HealResult` gains no `confidence` field.** `HealResult` is the loop's factual record of
   what happened; `HealAssessment` is a derived judgement about it. Keeping them in separate
   types and separate files is what makes "confidence never came from the model" auditable by
   reading one small file.

2. **`deriveConfidence` is pure and total.** It takes a `ConfidenceSignals` value and returns a
   `ConfidenceVerdict`. No I/O, no clock, no randomness, no `HealResult`, no transcript. Same
   input ⇒ same output, always.

3. **A verified fix is never graded `none`.** `none` means "no verified pass within the cap"
   (`DESIGN.md`). Downgrading a verified, executed, passing fix to `none` would throw away a real
   fix. `verified === true` ⟹ `confidence !== 'none'` is an asserted invariant.

4. **`prEligible` is the only PR authorisation.** It equals `confidence === 'high'` and nothing
   else. Task 5.1 must call `assertPrEligible` before it creates a branch. The tool still never
   auto-merges; `prEligible` means "may open a PR for a human", not "may land".

5. **Status values are the DESIGN.md column values verbatim**, snake_case included:
   `'investigating' | 'healed' | 'needs_review' | 'failed'`. `deriveConfidence` never returns
   `'investigating'` — that is a Task 4.2 persistence state for an in-flight row.

6. **One thresholds constant.** `CONFIDENCE_THRESHOLDS` is the single source of both numbers.
   `deriveConfidence`'s body contains no numeric literal at all.

7. **The measurement is not a tool call.** It is model-free, does not appear in
   `transcript.toolCalls`, does not increment `toolCallCount`, and does not count against
   `MAX_TOOL_CALLS`. Same precedent as the bootstrap DOM snapshot.

8. **No retry, no re-measure, no second query.** `measureVerifiedFix` queries once. A failure to
   measure is a recorded `measured: false`, which grades `low`.

9. **`scenario-matrix.ts` is untouched.** Scenario 3's `requiredOutcome` stays `'either'`, and
   `evaluateScenario` stays confidence-blind. Making the matrix confidence-aware would re-open a
   Task 3.3 decision and is explicitly out of scope.

10. **No new npm script and no new dependency.** `package.json` is unmodified.

### 1. Create `agent/loop/confidence.ts`

**The complete import list for this file is exactly one line:**


#### 1a. Types and the thresholds constant

```ts
export type ConfidenceLevel = 'high' | 'low' | 'none';

/** The DESIGN.md `heal_attempts.status` enum, verbatim. */
export type HealStatus = 'investigating' | 'healed' | 'needs_review' | 'failed';

export type ConfidenceReason =
  | 'no-verified-fix'
  | 'heal-error'
  | 'cap-reached-without-fix'
  | 'match-count-unavailable'
  | 'no-match-on-idle-page'
  | 'ambiguous-match'
  | 'too-many-tool-calls';

/**
 * The only place either threshold appears. `deriveConfidence` contains no numeric literal.
 */
export const CONFIDENCE_THRESHOLDS = {
  /** A high-confidence fix must resolve to exactly this many elements on the page. */
  exactMatchCount: 1,
  /** A high-confidence fix must be reached within this many model-initiated tool calls. */
  maxToolCallsForHigh: 2,
} as const;
```

#### 1b. The measurement

```ts
export interface VerifiedFixMeasurement {
  /** The verified selector that was measured, verbatim. */
  readonly selector: string;
  /** Elements matching `selector` on the live page. null if and only if `measured` is false. */
  readonly matchCount: number | null;
  /** False when the query threw or returned a structured selector error. */
  readonly measured: boolean;
  /** null if and only if `measured` is true. */
  readonly error: string | null;
  readonly measuredAt: string;
  readonly durationMs: number;
}

/**
 * Measure how many elements the verified selector matches, once, deterministically, with no
 * model involvement. Returns null when there is no verified fix to measure. Never throws.
 * This is not a model-initiated tool call: it is not recorded in the transcript and does not
 * count against MAX_TOOL_CALLS.
 */
export async function measureVerifiedFix(
  toolbox: HealToolbox,
  result: HealResult,
): Promise<VerifiedFixMeasurement | null>;
```

Body, exactly:

1. If `result.proposedSelector === null` → return `null` immediately. Do **not** call the
   toolbox.
2. `const selector = result.proposedSelector; const measuredAt = new Date().toISOString(); const t = Date.now();`
3. `try { const r = await toolbox.querySelector(selector); ... } catch (error) { ... }`
4. On success **and** `r.error === null`:
   `{ selector, matchCount: r.matchCount, measured: true, error: null, measuredAt, durationMs: Date.now() - t }`
5. On success **but** `r.error !== null`:
   `{ selector, matchCount: null, measured: false, error: r.error.message, measuredAt, durationMs: Date.now() - t }`
   (Conservative on purpose: a selector the browser could not evaluate is not a selector we
   grade `high`.)
6. On throw:
   `{ selector, matchCount: null, measured: false, error: error instanceof Error ? error.message : String(error), measuredAt, durationMs: Date.now() - t }`

Exactly one `querySelector` call per invocation. No loop, no retry, no timeout wrapper.

#### 1d. The rules

```ts
export interface ConfidenceVerdict {
  readonly confidence: ConfidenceLevel;
  readonly status: HealStatus;
  /** Identical to `confidence === 'high'`. The only PR authorisation in the system. */
  readonly prEligible: boolean;
  /** Empty if and only if `confidence === 'high'`. Ordered as evaluated. */
  readonly reasons: readonly ConfidenceReason[];
  /** `reasons.join(',')`, or null when `reasons` is empty. Maps to heal_attempts.failure_reason. */
  readonly failureReason: string | null;
}

/** Pure. No I/O, no clock, no randomness. The whole gate. */
export function deriveConfidence(signals: ConfidenceSignals): ConfidenceVerdict;
```

Body, exactly this shape and this evaluation order:

```ts
const reasons: ConfidenceReason[] = [];

if (!signals.verified || signals.proposedSelector === null) {
  reasons.push('no-verified-fix');
  if (signals.outcome === 'error') reasons.push('heal-error');
  if (signals.capReached) reasons.push('cap-reached-without-fix');
  return {
    confidence: 'none',
    status: 'failed',
    prEligible: false,
    reasons,
    failureReason: reasons.join(','),
  };
}

if (!signals.matchMeasured || signals.matchCount === null) {
  reasons.push('match-count-unavailable');
} else if (signals.matchCount !== CONFIDENCE_THRESHOLDS.exactMatchCount) {
  reasons.push(
    signals.matchCount < CONFIDENCE_THRESHOLDS.exactMatchCount
      ? 'no-match-on-idle-page'
      : 'ambiguous-match',
  );
}

if (signals.toolCallCount > CONFIDENCE_THRESHOLDS.maxToolCallsForHigh) {
  reasons.push('too-many-tool-calls');
}

if (reasons.length === 0) {
  return {
    confidence: 'high',
    status: 'healed',
    prEligible: true,
    reasons: [],
    failureReason: null,
  };
}

return {
  confidence: 'low',
  status: 'needs_review',
  prEligible: false,
  reasons,
  failureReason: reasons.join(','),
};
```

No other branch. No numeric literal anywhere in this function.

#### 1e. The assessment

```ts
export interface HealAssessment {
  /** The exact HealResult that was assessed, by reference. Never a copy or a subset. */
  readonly result: HealResult;
  readonly measurement: VerifiedFixMeasurement | null;
  readonly signals: ConfidenceSignals;
  readonly confidence: ConfidenceLevel;
  readonly status: HealStatus;
  readonly prEligible: boolean;
  readonly reasons: readonly ConfidenceReason[];
  readonly failureReason: string | null;
}

export function assessHealResult(
  result: HealResult,
  measurement: VerifiedFixMeasurement | null,
): HealAssessment;
```

Body: `const signals = collectConfidenceSignals(result, measurement);`
`const verdict = deriveConfidence(signals);`
assemble `{ result, measurement, signals, ...verdict }`, call
`assertConfidenceInvariant(assessment)`, then return it.

#### 1f. The two guards

```ts
/** Defence in depth. Throws if the gate produced a self-contradictory assessment. */
export function assertConfidenceInvariant(assessment: HealAssessment): void;
```

Checks, in this order, each throwing `new Error('confidence invariant violated: <text>')`:

1. `assessment.prEligible !== (assessment.confidence === 'high')` →
   `'prEligible !== (confidence === high)'`
2. `assessment.confidence === 'high'` and any of the following is false →
   `'high requires a verified single-match fix within the tool budget'`:
   `assessment.result.verified === true`,
   `assessment.result.proposedSelector !== null`,
   `assessment.result.verification?.passed === true`,
   `assessment.measurement !== null`,
   `assessment.measurement.measured === true`,
   `assessment.measurement.matchCount === CONFIDENCE_THRESHOLDS.exactMatchCount`,
   `assessment.result.toolCallCount <= CONFIDENCE_THRESHOLDS.maxToolCallsForHigh`
3. `assessment.confidence === 'none'` and not
   (`assessment.result.proposedSelector === null` && `assessment.prEligible === false` &&
   `assessment.status === 'failed'`) → `'none must have no proposed selector and no PR path'`
4. `assessment.result.verified === true && assessment.confidence === 'none'` →
   `'a verified fix must never be graded none'`
5. status/confidence map mismatch (`high`→`healed`, `low`→`needs_review`, `none`→`failed`) →
   `'status does not match confidence'`
6. `(assessment.reasons.length === 0) !== (assessment.confidence === 'high')` →
   `'reasons empty iff confidence is high'`
7. `(assessment.failureReason === null) !== (assessment.confidence === 'high')` →
   `'failureReason null iff confidence is high'`

```ts
/**
 * The gate Task 5.1 must call before creating a branch, committing, or opening a PR.
 * Throws unless the assessment is high-confidence and every underlying condition holds.
 */
export function assertPrEligible(assessment: HealAssessment): void;
```

Body: call `assertConfidenceInvariant(assessment)` first, then throw
`new Error(\`PR gate refused: confidence=\${assessment.confidence} status=\${assessment.status}\`)`
unless `assessment.prEligible === true && assessment.confidence === 'high'`.

#### 1g. Aggregation

```ts
export interface ConfidenceTotals {
  readonly attempts: number;
  readonly high: number;
  readonly low: number;
  readonly none: number;
  /** Always equal to `high`. Present so the PR gate's cardinality is visible in reports. */
  readonly prEligible: number;
}

export function summariseConfidence(
  assessments: readonly HealAssessment[],
): ConfidenceTotals;
```

Single pass counting by `confidence`, plus `prEligible` counted from the `prEligible` flag (not
copied from `high` — the point is that a report would show a discrepancy if the two ever
diverged). `summariseConfidence([])` returns all zeros.

Every type in this file must be JSON-serializable: no `Date`, no `Map`, no `undefined` fields.

```ts
// ---------- agent/loop/confidence.ts ----------

export type ConfidenceLevel = 'high' | 'low' | 'none';

  | 'no-verified-fix'
  | 'heal-error'
  | 'cap-reached-without-fix'
  | 'match-count-unavailable'
  | 'no-match-on-idle-page'

  readonly matchCount: number | null;
  readonly measured: boolean;
  readonly error: string | null;
  readonly measuredAt: string;
  readonly durationMs: number;
}

  readonly proposedSelector: string | null;
  readonly toolCallCount: number;
  readonly matchCount: number | null;
  readonly matchMeasured: boolean;
  readonly capReached: boolean;
  readonly outcome: HealOutcome;
  readonly stopReason: HealStopReason;
```

- **Temptation to put `confidence` on `HealResult`.** It would be one less type, and it would
  destroy the property that makes this task auditable: that the gate's entire input surface is a
  single eight-field struct with no model text in it. If the compiler seems to want it there,
  the fix is at the call site, not in `types.ts`.

- **Temptation to treat a `low` result as a failure.** `low` has a real, executed, passing,
  assertion-integrity-checked fix. It is routed to human review, not thrown away. Grading a
  verified fix as `none` is an invariant violation and `assertConfidenceInvariant` will throw.

- **`prEligible` misread as "will open a PR".** It means "may open a PR for a human to review".
  A human still merges, always. Task 5.1 must call `assertPrEligible` first; if it does not, that
  is a Task 5.1 review failure, and this plan's job is to make the guard exist and be exported.

- **The extra `query_selector` shows up in `fakeToolbox.calls()`.** Existing Task 3.3 tests that
  assert on `calls()` all use `healFailure` directly rather than the queue runner, so none of
  them regress — but if `npm run test:tools` reports a pre-existing test failing on a call count,
  do **not** edit that test. Report it as **Blocked / unclear**; it means the measurement was
  wired into the wrong layer.

- **`assessments` diverging from `results`.** The two arrays are pushed in the same branches and
  must never diverge. The `createToolbox`-throws branch is the easy one to forget, because it
  `continue`s. Push both before the `continue`.
