# Plan: 3.2 — Tool-calling loop against scenario 1 only

## Goal

After this task the repository can take one `ClassifiedFailure` from the Task 3.1 heal queue
— specifically scenario 1, the renamed `id` (`#login-btn` → `#signin-button`) — hand it to a
hand-rolled OpenAI tool-calling loop, and get back a `HealResult` whose `proposedSelector` is
non-null **only** because `run_single_test` was actually invoked and reported `passed === true`.
The loop executes at most `MAX_TOOL_CALLS = 5` model-initiated tool calls, counted before
execution so the cap holds on the failure path as well as the happy path, and terminates on
every route with a named `stopReason`. The full ordered transcript — every tool call, its
verbatim arguments, its structured result, and every model turn's usage — is returned in
memory as a JSON-serializable structure. No database, no confidence value, no PR, no scenarios
2–5.

---

## Read this before you start: the two ways to ruin this task

**1. Returning a selector the model merely asserted.** The model will, at some point, say
"the correct selector is `#signin-button`" in prose without ever calling `run_single_test`, or
call it and get `passed: false` and then insist it works anyway. `HealResult.proposedSelector`
must be `null` in both cases. There is exactly **one** place in the entire codebase where a
proposed selector becomes accepted, and it is guarded by `runResult.passed === true`. If you
find yourself parsing a selector out of the model's message text, stop — you have gone wrong.

**2. Making the cap advisory.** The counter increments *before* the tool runs, not after, and
not only when the tool succeeds. A tool call with unparseable arguments, an unknown tool name,
or a tool that throws all still consume one of the five. Hitting the cap is a normal, recorded
outcome (`stopReason: 'tool-call-cap-reached'`), not an error and not something to retry
around.

### Q1 — How is "heals scenario 1 end to end, verified by execution" verified, given it needs a real API call?

`npm run test:tools` must stay runnable offline, deterministically, with no API key and no
spend. But the acceptance criterion requires a real heal.

| Option | Mechanism | Trade-off |
| --- | --- | --- |
| **A (recommended)** | Two separate surfaces. (i) **Unit tests** (`npm run test:tools`) drive the loop with an injected `ScriptedModelClient` and a `FakeToolbox` — zero network, zero key, fully deterministic, and this is where cap exhaustion and the verification gate are proven. (ii) **A CLI**, `npm run heal:one -- --spec=tests/login-submit.spec.ts`, performs the real heal against the real model, the real browser, and the real `run_single_test`; exit `0` means healed. The Builder runs it and pastes the output; the Reviewer re-runs it. | Both criteria are met by the surface suited to each. The offline test suite never becomes flaky or costly. The live run is one command, reproducible by anyone with a key. |
| B | One Playwright spec that calls the real API, `test.skip()`-ed when `OPENAI_API_KEY` is absent. | Makes `npm run test:tools` non-deterministic and network-dependent, and silently green on a machine with no key — the worst failure mode for an acceptance criterion. |
| C | Record/replay HTTP fixtures of the OpenAI call. | Invents a cassette format and a recording workflow for one scenario. Large amount of machinery; the fixture is stale the moment the prompt changes. |

Recommendation: **A**.

### Q2 — The `openai` npm SDK, or raw `fetch`?

DESIGN.md says "OpenAI API with native tool calling … No agent framework. The loop is ~100
lines of explicit control flow." The SDK is a client, not a framework, so it is not forbidden —
but the repository currently has **zero** runtime dependencies and no `dependencies` key at all.

| Option | Trade-off |
| --- | --- |
| **A (recommended) — raw `fetch`** | One `POST` to `https://api.openai.com/v1/chat/completions`, no streaming, ~50 lines including response parsing. Node ≥18.17 (already the declared engine) has global `fetch` and `AbortSignal.timeout`. Zero new dependencies, no `dependencies` key introduced, no supply-chain surface, and the wire shape stays visible — which is the stated point of hand-rolling the loop. |
| B — `openai` SDK | Slightly less parsing code; adds the project's first runtime dependency and hides the request shape behind a typed facade. |

Recommendation: **A**. If option B is chosen, only `agent/loop/openai-client.ts` changes; the
`ModelClient` interface is deliberately SDK-agnostic so this is a one-file swap.

### Q3 — Model selection, API key handling, and a cost bound

None of the three spec files name a model, a key mechanism, or a budget.

Recommendation, all three parts:

- **Model:** one exported constant `DEFAULT_HEAL_MODEL = 'gpt-4o-mini'` in
  `agent/loop/openai-client.ts`, overridable at runtime by the `MEND_OPENAI_MODEL` environment
  variable. The chosen model is echoed in `HealResult.model`. If the API rejects
  `gpt-4o-mini`, or rejects the `temperature` / `parallel_tool_calls` parameters, the Builder
  **reports it as Blocked / unclear with the verbatim API error** and does not silently pick a
  different model or drop a parameter.
- **Key:** read from `process.env['OPENAI_API_KEY']` at client-construction time only. No
  `.env` file loading, no `dotenv` dependency, no key in any constructor argument, log line,
  transcript field, or error message. Missing key → the client factory throws a message naming
  the variable and nothing else.
- **Cost bound:** the live heal (Q1) is run **at most 3 times** during the build — once to
  confirm, plus at most two retries if it fails. Per-turn token usage is captured in
  `HealResult.transcript.modelRequests[].usage`; the Builder pastes the totals into the build
  report. If three live runs do not produce `outcome: 'healed'`, that is a **Blocked / unclear**
  report with the transcript attached, not a fourth attempt and not a prompt-tuning spiral.

### Q4 — Is the DOM snapshot pre-injected, or must the model call `get_dom_snapshot`?

DESIGN.md's pipeline reads `Failure context + DOM snapshot ↓ OpenAI agent loop (max 5 tool
calls)`, which implies the snapshot arrives *with* the context. But `get_dom_snapshot` is also
one of the three registered tools.

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| **A (recommended)** | The loop captures **one** bootstrap snapshot itself, before the first model request, and embeds it in the initial user message. `get_dom_snapshot` is *still* registered as a callable tool (for re-reading the DOM), but the bootstrap capture is not a model-initiated call and does not consume the cap. | Matches DESIGN.md's pipeline diagram literally. It is also the only reading consistent with the Task 3.4 confidence table: `high` requires "verified pass, **exactly 1 DOM match**, **≤ 2 tool calls**", which is reachable only as `query_selector` (gives the match count) + `run_single_test` (gives the verified pass) = 2 calls. `breakage/README.md` says scenario 1 must land on high confidence, so this is effectively forced. The bootstrap capture is exactly one, deterministic, bounded to 4000 estimated tokens, and is recorded in the transcript so the dashboard can still replay "the DOM the agent saw". |
| B | No pre-injection; the model must spend a tool call on `get_dom_snapshot`. | The cheapest successful path becomes 3 tool calls (snapshot, query, run), which makes scenario 1 `low` confidence under DESIGN.md's table and contradicts `breakage/README.md`. |

Recommendation: **A**. Note this does not make the cap softer: it is one fixed, model-free
capture, in the same category as the rule-based classifier.

## Architectural decisions already made (do not revisit)

1. **The loop never touches Playwright, the browser, or the OpenAI wire format directly.** It
   depends on two injected interfaces, `ModelClient` and `HealToolbox`. This is what makes the
   cap and the verification gate testable without a network or a browser, and it is why the
   unit tests are deterministic.

2. **The model cannot choose *what* is verified, only *with what*.** `HealToolbox.runSingleTest`
   takes a single `candidateSelector: string`. `specFile`, `testName`, and `originalSelector`
   are captured from the `ClassifiedFailure` when the toolbox is constructed and are
   unreachable from the model. A model that sends `{"candidate":"#x","specFile":"tests/evil.spec.ts"}`
   gets its extra keys ignored. This is asserted by a unit test.

3. **`verifiedFix` is assigned in exactly one place**, inside a branch guarded by
   `runResult.passed === true`, immediately after a `run_single_test` execution.
   `HealResult.proposedSelector` is `verifiedFix?.candidateSelector ?? null` and is derived
   from nothing else — never from `response.content`, never from the tool call's arguments
   alone, never from a `query_selector` result.

4. **The tool-call counter increments before execution, unconditionally.** Unknown tool name,
   malformed JSON arguments, and a tool that throws all consume one call. There is no path
   where a tool executes without having been counted.

5. **A passing `run_single_test` terminates the loop immediately.** No further tool calls, no
   further model requests. Success is an exit, not a checkpoint.

6. **When the cap is reached, no further model request is made.** Another turn could not act,
   so it would only cost money. The loop breaks with `stopReason: 'tool-call-cap-reached'`.

7. **`maxToolCalls` can only be lowered, never raised.** The effective cap is
   `Math.min(deps.maxToolCalls ?? MAX_TOOL_CALLS, MAX_TOOL_CALLS)`. A caller passing `99` still
   gets `5`. Asserted by a unit test.

8. **Zero retry logic.** A model API error, a browser error, or a tool throwing does not trigger
   a re-attempt at any level. Errors are recorded and either returned to the model as tool
   feedback (tool errors) or terminate the attempt (model/bootstrap errors).

9. **The transcript is JSON-serializable and jsonb-ready.** No `Date` objects, no `Map`, no
   `undefined` in any recorded field, no functions, no circular references. Timestamps are ISO
   8601 strings. Task 4.2 will store it verbatim.

10. **No scenario-specific logic.** `agent/loop/*.ts` (outside `__tests__/` and `README.md`)
    contains no occurrence of `#login-btn`, `#signin-button`, `login-submit`, or any other
    scenario literal. The loop is generic; the *task* is narrowed to scenario 1 by which
    failure the CLI is pointed at, not by branching.

11. **No new npm dependency.** Node builtins and global `fetch` only. `devDependencies` is
    unchanged and no `dependencies` key is introduced.

12. **The loop produces no `confidence` and no `status`.** Those are Task 3.4 and Task 4.2.
    `HealResult` has no such fields.

**Functions:**

```ts
export function isHealToolName(name: string): name is HealToolName;
```
`HEAL_TOOL_NAMES.includes(name as HealToolName)`.

```ts
export function parseToolArguments(
  tool: HealToolName,
  argumentsJson: string,
): ToolArgumentsParseResult;
```
Never throws. Steps:
1. If `tool === 'get_dom_snapshot'`: return `{ ok: true, args: {}, value: null, error: null }`
   regardless of what was sent (an empty-arg tool is not worth failing over). If
   `argumentsJson` is non-empty and parses to an object, put it in `args`; otherwise `args` is `{}`.
2. Otherwise `JSON.parse(argumentsJson || '{}')`. On throw →
   `{ ok: false, args: {}, value: null, error: 'arguments are not valid JSON' }`.
3. If the parsed value is not a non-null non-array object →
   `{ ok: false, args: {}, value: null, error: 'arguments must be a JSON object' }`.
4. Field name is `'selector'` for `query_selector` and `'candidate'` for `run_single_test`.
   If the field is missing, not a `string`, or `.trim()` is empty →
   `{ ok: false, args: parsed, value: null, error: \`missing or empty "\${field}"\` }`.
5. Otherwise `{ ok: true, args: parsed, value: <the string, verbatim and untrimmed>, error: null }`.

Extra keys the model sends are preserved in `args` (so the transcript is honest) and otherwise
**ignored**. They are never forwarded to any tool.

```ts
export function summariseToolResult(record: ToolCallResult): string;
```
Returns the exact string used as the `content` of the `tool` message sent back to the model.
Always valid JSON. Shapes, by `record.kind`:

- `'dom-snapshot'` → `JSON.stringify({ url, estimatedTokens, elementCount, truncated, html })`
  where `html` is `clampHead(snapshot.html, MAX_TOOL_RESULT_CHARS)`.
- `'query-selector'` → `JSON.stringify({ selector, matchCount, previews, previewsTruncated, error })`
  taken straight from `QuerySelectorResult`.
- `'run-single-test'` → `JSON.stringify({ candidate, passed, executed, rejected, violations, changedLineCount, outputTail })`
  where `changedLineCount = result.changedLines.length` and
  `outputTail = clampTail(result.output, MAX_TEST_OUTPUT_TAIL_CHARS)`.
- `'error'` → `JSON.stringify({ error: record.message })`.

Private helpers, not exported:
```ts
function clampHead(text: string, max: number): string;  // text.slice(0, max) + '\n…[truncated]…' when longer
function clampTail(text: string, max: number): string;  // '…[truncated]…\n' + text.slice(-max) when longer
```

```ts

```

```ts
export function createOpenAIClient(overrides?: {
  readonly model?: string;
  readonly apiKey?: string;
  readonly timeoutMs?: number;
}): ModelClient;
```
- `const apiKey = overrides?.apiKey ?? process.env['OPENAI_API_KEY'] ?? '';`
- If `apiKey.trim() === ''` throw
  `new Error('OPENAI_API_KEY is not set; export it before running a heal')`. The message must
  not contain any part of a key value.
- `const model = overrides?.model ?? resolveHealModel();`
- Returns `{ model, createCompletion }`.

`createCompletion(request)`:
1. `POST` to `OPENAI_CHAT_COMPLETIONS_URL` with headers
   `{ 'content-type': 'application/json', authorization: \`Bearer \${apiKey}\` }` and
   `signal: AbortSignal.timeout(overrides?.timeoutMs ?? MODEL_REQUEST_TIMEOUT_MS)`.
2. Body: `JSON.stringify({ model, messages: request.messages, tools: request.tools, tool_choice: 'auto', temperature: 0, parallel_tool_calls: false })`.
3. If `!response.ok`: read the body as text, clamp it to 1000 chars, and throw
   `new Error(\`OpenAI request failed: \${response.status} \${clampedBody}\`)`. Never include
   the request headers or body in the message.
4. Parse JSON. Read `choices[0]` defensively (`noUncheckedIndexedAccess` is on). If there is no
   `choices[0].message`, throw `new Error('OpenAI response contained no choices')`.
5. Map to `ModelResponse`:
   - `content: message.content ?? null`
   - `toolCalls`: `(message.tool_calls ?? [])` mapped to
     `{ id: tc.id ?? '', name: tc.function?.name ?? '', argumentsJson: tc.function?.arguments ?? '' }`
   - `finishReason: choices[0].finish_reason ?? 'unknown'`
   - `usage`: `{ promptTokens, completionTokens, totalTokens }` from `body.usage`
     (`prompt_tokens`, `completion_tokens`, `total_tokens`), or `null` when absent.

This is the only file permitted to reference `process.env['OPENAI_API_KEY']`, `fetch`, or an
`https://` URL.

### 6. Create `agent/loop/heal-loop.ts` — the core

**Constants (exported, named, no scattered literals):**

```ts
export async function healFailure(
  failure: ClassifiedFailure,
  deps: HealDeps,
): Promise<HealResult>;
```

Local mutable state, declared at the top of the function:
```ts
const startedAt = new Date().toISOString();
const t0 = Date.now();
const cap = Math.min(deps.maxToolCalls ?? MAX_TOOL_CALLS, MAX_TOOL_CALLS);

const messages: ChatMessage[] = [];
const toolCalls: ToolCallRecord[] = [];
const modelRequests: ModelRequestRecord[] = [];

let toolCallCount = 0;
let modelTurnCount = 0;
let capReached = false;
let verifiedFix: VerifiedFix | null = null;
let verification: VerificationSummary | null = null;
let stopReason: HealStopReason = 'model-turn-limit-reached';
let errorMessage: string | null = null;
let bootstrapSnapshot: BootstrapSnapshot | null = null;
```

**Step 6a — validate the input.** If `failure.classification !== 'selector-drift'`, or
`failure.selector === null`, or `failure.selector.trim() === ''`, or
`failure.specFile.trim() === ''`, or `failure.testName.trim() === ''`, return immediately with
`outcome: 'error'`, `stopReason: 'invalid-input'`, `errorMessage` naming the offending field,
`toolCallCount: 0`, and an empty transcript. Do not construct a toolbox, do not call the model.

**Step 6b — bootstrap snapshot.** Inside `try/catch`:
```ts
const snapshot = await deps.toolbox.getDomSnapshot();
bootstrapSnapshot = {
  url: snapshot.url,
  html: snapshot.html,
  estimatedTokens: snapshot.estimatedTokens,
  elementCount: snapshot.elementCount,
  truncated: snapshot.truncated,
  capturedAt: snapshot.capturedAt,
};
```
On throw: `errorMessage = <message>`, `stopReason = 'toolbox-error'`, and return with
`outcome: 'error'`. This capture does **not** increment `toolCallCount` (see Q4).

**Step 6c — seed the conversation.**
`messages.push(...buildInitialMessages(failure, deps.appUrl, snapshot));`

**Step 6d — the loop.** A labelled outer `for` so the inner tool loop can break out of both:

```ts
turnLoop: for (let turn = 1; turn <= MAX_MODEL_TURNS; turn++) {
  modelTurnCount = turn;

  let response: ModelResponse;
  try {
    response = await deps.model.createCompletion({ messages, tools: HEAL_TOOL_SCHEMAS });
  } catch (error) {
    errorMessage = error instanceof Error ? error.message : String(error);
    stopReason = 'model-error';
    break turnLoop;
  }

  modelRequests.push({
    turn,
    finishReason: response.finishReason,
    usage: response.usage,
    contentPreview: (response.content ?? '').slice(0, 500),
    requestedTools: response.toolCalls.map((c) => c.name),
  });

  messages.push({
    role: 'assistant',
    content: response.content,
    ...(response.toolCalls.length > 0
      ? {
          tool_calls: response.toolCalls.map((c) => ({
            id: c.id,
            type: 'function' as const,
            function: { name: c.name, arguments: c.argumentsJson },
          })),
        }
      : {}),
  });

  if (response.toolCalls.length === 0) {
    stopReason = 'model-gave-up';
    break turnLoop;
  }

  for (const call of response.toolCalls) {
    if (toolCallCount >= cap) {
      capReached = true;
      stopReason = 'tool-call-cap-reached';
      break turnLoop;
    }

    toolCallCount += 1;                                   // counted BEFORE execution
    const record = await executeToolCall(deps.toolbox, call, toolCallCount);
    toolCalls.push(record);
    messages.push({ role: 'tool', tool_call_id: call.id, content: record.resultSummary });

    if (record.result.kind === 'run-single-test') {
      verification = {
        candidateSelector: record.result.candidate,
        passed: record.result.passed,
        executed: record.result.executed,
        rejected: record.result.rejected,
        changedLines: record.result.changedLines,
        output: record.result.output,
        durationMs: record.durationMs,
      };

      // THE VERIFICATION GATE. The only assignment to verifiedFix in this codebase.
      if (record.result.passed === true) {
        verifiedFix = { candidateSelector: record.result.candidate, toolCallIndex: toolCallCount };
        stopReason = 'verified-fix';
        break turnLoop;
      }
    }
  }

  if (toolCallCount >= cap) {
    capReached = true;
    stopReason = 'tool-call-cap-reached';
    break turnLoop;
  }
}
```

Two details that are not optional:
- The `if (toolCallCount >= cap)` check **after** the inner loop is what stops a sixth model
  request being paid for when no call remains. Keep it.
- `stopReason` is initialised to `'model-turn-limit-reached'`, which is therefore the value if
  the `for` runs to completion.

**Step 6e — build the result.**
```ts
const outcome: HealOutcome =
  verifiedFix !== null ? 'healed' : errorMessage !== null ? 'error' : 'no-fix';

const result: HealResult = {
  specFile: failure.specFile,
  testName: failure.testName,
  originalSelector: failure.selector ?? '',
  proposedSelector: verifiedFix?.candidateSelector ?? null,
  outcome,
  stopReason,
  verified: verifiedFix !== null,
  toolCallCount,
  capReached,
  modelTurnCount,
  verification,

  model: deps.model.model,
  startedAt,

```

**Step 6f — `assertHealInvariant`.** Exported, synchronous, throws on violation. Defence in
depth; it should be unreachable.
```ts
export function assertHealInvariant(result: HealResult): void;
```
Throws `new Error('heal invariant violated: <detail>')` if any of these is false:
- `(result.proposedSelector !== null) === (result.outcome === 'healed')`
- `(result.proposedSelector !== null) === result.verified`
- `result.proposedSelector === null || result.verification?.passed === true`
- `result.proposedSelector === null || result.verification?.candidateSelector === result.proposedSelector`
- `result.toolCallCount <= MAX_TOOL_CALLS`
- `result.transcript.toolCalls.length === result.toolCallCount`

**Step 6g — `executeToolCall`.** Private to `heal-loop.ts`, not exported.
```ts
async function executeToolCall(
  toolbox: HealToolbox,
  call: ModelToolCall,
  index: number,
): Promise<ToolCallRecord>;
```
Never throws. Steps:
1. `const startedAt = new Date().toISOString(); const t = Date.now();`
2. If `!isHealToolName(call.name)` → build a record with `ok: false`,
   `result: { kind: 'error', message: \`unknown tool: \${call.name}\` }`.
3. `const parsed = parseToolArguments(call.name, call.argumentsJson);`
   If `!parsed.ok` → `ok: false`, `result: { kind: 'error', message: parsed.error }`.
4. Dispatch inside `try/catch`; a throw yields `ok: false`,
   `result: { kind: 'error', message: <error message> }`:
   - `get_dom_snapshot` → `const s = await toolbox.getDomSnapshot();` →
     `{ kind: 'dom-snapshot', url: s.url, html: s.html, estimatedTokens: s.estimatedTokens, elementCount: s.elementCount, truncated: s.truncated }`
   - `query_selector` → `const r = await toolbox.querySelector(parsed.value);` →
     `{ kind: 'query-selector', selector: r.selector, matchCount: r.matchCount, previews: r.previews, previewsTruncated: r.previewsTruncated, error: r.error }`
   - `run_single_test` → `const r = await toolbox.runSingleTest(parsed.value);` →
     `{ kind: 'run-single-test', candidate: parsed.value, passed: r.passed, executed: r.executed, rejected: r.rejected, violations: r.violations, changedLines: r.changedLines, output: r.output }`
5. Return:
```ts
{
  index,
  toolCallId: call.id,
  tool: call.name,
  rawArguments: call.argumentsJson,
  arguments: parsed.args,
  ok,
  result,
  resultSummary: summariseToolResult(result),
  startedAt,
  durationMs: Date.now() - t,
}
```
`tool` is typed `HealToolName | string`; for the unknown-tool case store `call.name` verbatim.

Note `run-single-test`'s `passed` is copied straight from `RunSingleTestResult.passed` — it is
never recomputed, never inferred from `output`, and never OR-ed with anything.

```ts
export interface ScriptedTurn {
```

- Returns turn *n* on the *n*-th `createCompletion` call.

## Risks

- **Returning a selector the model only claimed.** The single most likely way this task is
  ruined. Mitigated by decision 3, the single-assignment rule, `assertHealInvariant`, and unit
  tests (4), (5), (6), and (18). If the Builder finds itself writing anything that reads a
  selector out of `response.content`, stop and report **Blocked / unclear**.

- **A soft cap.** The second most likely failure. Counting after execution, or only counting
  successful calls, would let a model burn arbitrary calls by sending malformed arguments. Test
  (2)'s `toolbox.calls().length === 5` assertion is what catches it — it checks *execution*, not
  bookkeeping. Do not weaken that assertion to `toolCallCount === 5`.

- **Paying for a model turn that cannot act.** Without the post-inner-loop cap check in step 6d,
  the loop makes a sixth request whose tool calls are all rejected. Keep the check.

- **Unanswered `tool_call` ids.** The OpenAI API requires every `tool_call` in an assistant
  message to be answered by a `tool` message before the *next* request. The loop only ever
  leaves calls unanswered when it is terminating and will make no further request, so this is
  safe. If the Builder is tempted to add a synthetic "cap reached" tool message to tidy this up,
  do not — it adds a message the model never sees and confuses the transcript.

- **The model refuses to call `run_single_test` and just narrates.** Handled: zero tool calls
  terminates with `model-gave-up` and no fix. If the live run hits this repeatedly, the fix is
  prompt rule 2 wording, not adding a fallback that verifies the model's suggestion on its
  behalf — that would move the decision to propose a candidate out of the model and is a design
  change, so report it rather than implementing it.

- **`temperature` or `parallel_tool_calls` rejected by the chosen model.** Some newer models
  reject one or both. Report the verbatim API error as **Blocked / unclear** rather than
  silently dropping the parameter — `temperature: 0` is what makes the live run roughly
  reproducible.

- **The app server not running during the bootstrap snapshot.** `run_single_test` starts its own
  server via `reuseExistingServer`, but `createPlaywrightToolbox` navigates directly and will
  fail with a connection error. The CLI must turn that into exit `1` with a message telling the
  user to run `npm run start:app`. Do not "fix" it by having the toolbox spawn a server.

- **Breakage left on.** Step 13 turns breakage on. The task must end with `npm run break:status`
  printing `pristine` and `git status --porcelain app-under-test/` empty. If
  `app-under-test/index.html` is already dirty at the *start* of the task, that is a
  **Blocked / unclear** report, not something to `git checkout` away.

- **Leaked API key.** Never log `process.env`, never include request headers in an error, never
  echo the `authorization` header. `.env` is gitignored as belt-and-braces. If a key ever
  appears in a build report, treat the key as compromised and say so.

- **`noUncheckedIndexedAccess` and `noUnusedLocals`.** Both are on. `choices[0]`,
  `response.toolCalls[i]`, and every array index need a guard, not a `!`. An unused `import
  type` is a build failure, not a warning.

- **Live-run flakiness burning budget.** Three live runs maximum (Q3). If the model picks a
  valid-but-different selector (e.g. `button#signin-button` or `form button[type="submit"]`)
  and `run_single_test` passes, that is a **success**, not a failure — the acceptance criterion
  that matters is `outcome=healed` with `verified=true`. The
  `proposed=#signin-button` expectation in step 13 is the expected value, and any other
  *verified-passing* selector should be reported in Deviations rather than retried against.

- **Scope creep into Task 3.3 or 3.4.** The moment the Builder writes a `confidence` variable, a
  second scenario's fixture, or a loop over `report.healQueue`, it has left this task.
