# Plan: 3.1 — Failure classifier

## Goal

After this task the repository can read a Playwright JSON report and split its failures into
two disjoint, ordered lists: a **heal queue** of `selector-drift` failures (each carrying the
exact spec file, test title, and the original selector literal extracted from the Playwright
error) and a **skipped** list of `other` failures (each carrying a machine-readable reason
code). Classification is 100% rule-based on the error text — no model, no network, no API
key, no `openai` import anywhere in the new code. Running the seeded breakage produces a heal
queue of exactly the five Task 1.3 scenarios with their five original selectors correctly
extracted; a non-selector failure (navigation error, page exception, value mismatch on an
element that *was* found) never appears in the heal queue. Nothing about the agent loop, the
model, persistence, or confidence is built here.

---

## Read this before you start: scenario 5 is `selector-drift`

The most likely way a Builder ruins this task is by reasoning "scenario 5 is unfixable, so it
must be classified as `other`". **That is wrong and it is an automatic FAIL.**

Scenario 5 (`#remember-me`, element removed) produces exactly the same Playwright error
signature as scenarios 3 and 4 — `expect(locator).toBeVisible() failed … element(s) not
found`. It *is* selector drift by every observable signal. It belongs in the heal queue. The
system's proof that "the agent knows when to stop" comes from the **agent** failing to find a
verified fix (Task 3.3), not from the classifier refusing to look at it. A classifier that
skips scenario 5 would be cheating: it would be using knowledge the error text does not
contain.

All five seeded scenarios classify as `selector-drift`. Zero classify as `other`.

## Open questions — answer at the approval gate

These are escalations, not decisions taken unilaterally. **If the human does not answer, the
recommendation stands and the Builder proceeds with it.** Everything below this section is
written assuming every recommendation is accepted.

**Q1 — What does "recorded" mean, given PostgreSQL does not exist until Phase 4?**

TASKS.md 3.1 says non-selector failures must be "skipped and recorded". There is no database,
no `runner/`, and no persistence layer yet.

| Option | Meaning of "recorded" | Trade-off |
| --- | --- | --- |
| **A (recommended)** | Every failure — including `other` ones — is present in the returned `ClassificationReport.skipped` array with its reason code and error text, and printed by the CLI. No file is written, no DB row is created. | Honest to the phase boundary. Task 4.2 persists the same structure verbatim. Nothing to migrate later. |
| B | The CLI also writes a `classification.json` artifact to disk. | Invents a persistence format that Phase 4 will immediately supersede, and creates a second source of truth. |
| C | Defer "recorded" entirely to Task 4.2 and return only the heal queue. | Loses the skipped failures' reasons at the point where they are known; makes the acceptance criterion unverifiable at 3.1. |

Recommendation: **A**. "Recorded" at 3.1 = present in the returned report and visible in CLI
output, with a stable shape Phase 4 can persist directly.

**Q2 — How is the classifier invoked? `runner/` does not exist.**

DESIGN.md puts detection inside "Runner", but Task 3.1 does not create a runner and no task
before Phase 3.2 does either.

Recommendation: ship a **pure library plus a thin CLI**, exactly matching the Phase 2 tool
convention (`agent/tools/*.ts` + `agent/tools/cli/*.cli.ts` + an npm script). The CLI reads
`test-results/results.json` (the path Task 1.2 fixed) and prints the classification. **Do not
create `runner/`.** Task 3.2 imports the library function; the CLI exists so this task is
verifiable standalone with no model, exactly like Phase 2's tools.

**Q3 — Where does the code live and how do its unit tests run?**

The classifier is not one of the three model-callable tools, so it does not belong in
`agent/tools/`. Its tests are pure and need no browser, but the repository has exactly one
unit-test command (`npm run test:tools`, driven by `playwright.tools.config.ts` with
`testDir: './agent/tools/__tests__'`).

Recommendation: new directory `agent/classifier/`, and widen `playwright.tools.config.ts`'s
`testDir` from `'./agent/tools/__tests__'` to `'./agent'` (one line). Playwright's default
`testMatch` then picks up both `agent/tools/__tests__/*.spec.ts` and
`agent/classifier/__tests__/*.spec.ts` and nothing else (`.cli.ts` and `.json` files do not
match). `npm run test:tools` stays the single unit-test command. Rejected alternative: a
fourth Playwright config plus a fourth npm script, for zero benefit.

**Q4 — Is "wrong element matched" selector drift?**

REQUIREMENTS.md lists "wrong element matched" among selector-resolution failures.
DESIGN.md names exactly three identifiable signatures: "strict mode violation, element not
found, timeout waiting for selector". These pull in different directions for the case where
a locator **did** resolve to an element but an `expect()` value assertion then failed (e.g.
`toHaveText` mismatch).

| Option | Behaviour | Trade-off |
| --- | --- | --- |
| **A (recommended)** | `other`, reason `element-resolved`. The Playwright call log line `locator resolved to <…>` is the decisive signal: the selector worked. | A value mismatch is indistinguishable from a genuine application bug by error string alone. Sending it to the model invites the agent to "heal" a real bug by re-pointing the selector at a different element — precisely the false fix that Task 7.1 requires to be 0. Matches DESIGN.md's three signatures literally. |
| B | `selector-drift`. | Covers REQUIREMENTS' "wrong element matched" phrase, at the cost of feeding genuine app failures to the model and risking false fixes. Also raises cost, which DESIGN.md's rule-based-classification rationale exists to bound. |

Recommendation: **A**. Note this does not affect any of the five seeded scenarios — scenario
4 (text drift) fails as *element not found*, because its locator is
`button:has-text("Sign In")`, so option A still classifies all five as `selector-drift`.
"Ambiguous match" (strict mode violation) remains `selector-drift` under option A; only the
element-found-but-value-wrong case is skipped.

## Architectural decisions already made (do not revisit)

1. **Classification is a pure function of the error text.** `classifyErrorText(errorText)`
   performs no I/O, is synchronous, and never reads a spec file, the DOM, the network, or the
   filesystem. Only `classifyResultsFile` touches the filesystem.

2. **A failure is `selector-drift` only if a selector literal was successfully extracted.**
   The heal queue's entire purpose is to feed `run_single_test`, which requires an
   `originalSelector`. A failure with a selector-drift signature but no extractable locator is
   `other`, reason `selector-not-extractable`. This is applied uniformly as a post-check.

3. **`locator resolved to` beats every selector signal.** If the call log says the locator
   resolved, the selector worked and the failure is not selector drift. See Q4.

4. **ANSI escape codes are stripped before any matching or extraction.** Playwright's JSON
   reporter embeds SGR colour codes inside error messages. Matching or extracting a selector
   from un-stripped text is a latent bug that would only show on some terminals/versions.

5. **Classification runs on the full error text; only the *stored* `errorText` is clamped.**
   Clamping first could delete the marker that decides the classification.

6. **Rule order is fixed and exported as one named constant.** No scattered literals, no
   re-ordering to make a test pass.

7. **`classifyFailures(report: unknown)` never throws.** Garbage input yields an empty report.
   Only `classifyResultsFile` throws (unreadable/unparseable file), and only the CLI turns
   that into an exit code.

8. **Fixtures are captured verbatim from real runs, never hand-written or hand-edited.** Two
   committed JSON fixtures (broken run, pristine run) make "correctly classifies all 5 seeded
   scenarios" a deterministic unit test that needs no browser. Hand-transcribing a fixture is
   forbidden — copy the file.

9. **The classifier does not verify that the extracted selector occurs in the spec file.**
   `run_single_test` already rejects `selector-not-found` and `selector-ambiguous`. Duplicating
   that here would couple the classifier to the filesystem for no gain.

10. **No new npm dependency.** Node builtins only.

### 2. Create `agent/classifier/failure-classifier.ts` — types and constants

Copy the type block from **Interfaces / types** below verbatim. Then declare exactly these
module constants:

```ts
export const DEFAULT_RESULTS_PATH = 'test-results/results.json';
export const MAX_ERROR_TEXT_CHARS = 8_000;

export const CLASSIFICATION_RULE_ORDER: readonly ClassificationRuleId[] = [
  'strict-mode-violation',
  'no-error-output',
  'navigation-failure',
  'page-exception',
  'element-resolved',
  'element-not-found',
  'timeout-waiting-for-locator',
  'test-timeout',
  'unrecognized',
];
```

Plus the private (non-exported) regex constants, exactly these:

```ts
const ANSI_SGR = /\[[0-9;]*m/g;
const STRICT_MODE = /strict mode violation/i;
const ELEMENT_NOT_FOUND = /element\(s\) not found|resolved to 0 elements/i;
const WAITING_FOR_LOCATOR = /waiting for locator\(/i;
const LOCATOR_RESOLVED = /locator resolved to/i;
const TIMEOUT_EXCEEDED = /Timeout \d+ms exceeded|Timeout:\s*\d+ms/i;
const TEST_TIMEOUT = /Test timeout of \d+ms exceeded/i;
const NAVIGATION_FAILURE = /page\.goto:|net::ERR_|NS_ERROR_/i;
const PAGE_EXCEPTION =
  /^(?:Error:\s*)?(?:ReferenceError|TypeError|SyntaxError|RangeError|EvalError|URIError):/;
const LOCATOR_SINGLE_QUOTED = /locator\(\s*'((?:[^'\\]|\\.)*)'\s*\)/;
const LOCATOR_DOUBLE_QUOTED = /locator\(\s*"((?:[^"\\]|\\.)*)"\s*\)/;
const LOCATOR_LINE = /^Locator:\s*(.+)$/;
const WAITING_FOR_SINGLE = /waiting for locator\(\s*'((?:[^'\\]|\\.)*)'\s*\)/;
const WAITING_FOR_DOUBLE = /waiting for locator\(\s*"((?:[^"\\]|\\.)*)"\s*\)/;
```

The colon in `page\.goto:` is load-bearing: it distinguishes the *error* `page.goto: net::…`
from a source snippet containing `await page.goto('/')`. Do not remove it.

`PAGE_EXCEPTION` is applied to the **first non-empty line only**, never to the whole text
(stack frames would produce false positives).

### 3. Implement `stripAnsi` and `extractSelector`

```ts
export function stripAnsi(text: string): string;
```
Returns `text.replace(ANSI_SGR, '')`. Idempotent. Never throws on empty string.

```ts
export function extractSelector(errorText: string): string | null;
```
Calls `stripAnsi` on its input first (so it is safe to call with raw text). Then, in this
exact priority order — first hit wins:

1. **`Locator:` line.** Split into lines. For the first line whose `.trim()` matches
   `LOCATOR_LINE`, take capture group 1 and test it against `LOCATOR_SINGLE_QUOTED` then
   `LOCATOR_DOUBLE_QUOTED`. If either matches, return its capture group 1. If the `Locator:`
   line contains no `locator(...)` literal, fall through to step 2 (do not return the raw
   remainder).
2. **Call log.** Test the whole text against `WAITING_FOR_SINGLE`, then `WAITING_FOR_DOUBLE`.
   Return the first capture group 1 found.
3. **Anywhere.** Test the whole text against `LOCATOR_SINGLE_QUOTED`, then
   `LOCATOR_DOUBLE_QUOTED`. Return the first capture group 1 found.
4. Return `null`.

Post-check applied to every returned value: if the captured string is empty after `.trim()`,
return `null` instead. The captured text is returned **verbatim** — no unescaping, no
trimming of the value itself, no quote normalisation.

### 4. Implement `collectErrorText` (private) and `collectErrorSignals`

```ts
function collectErrorText(result: RawTestResult): string;
```
Private, not exported. Builds an ordered list of candidate strings:
1. every `result.errors[i].message` in order,
2. `result.error?.message`,
3. `result.error?.stack`.

Drop `undefined`/`null`/empty-after-trim entries, then remove exact duplicates preserving
first occurrence, then `join('\n')`, then `stripAnsi`. Never read `result.error.snippet`
(source-code frames are noise and can contain misleading markers).

```ts
export function collectErrorSignals(errorText: string): ErrorSignals;
```
Pure. Calls `stripAnsi` on its input first. Computes:

| field | value |
| --- | --- |
| `hasLocator` | `extractSelector(text) !== null` |
| `strictModeViolation` | `STRICT_MODE.test(text)` |
| `elementNotFound` | `ELEMENT_NOT_FOUND.test(text)` |
| `waitingForLocator` | `WAITING_FOR_LOCATOR.test(text)` |
| `locatorResolved` | `LOCATOR_RESOLVED.test(text)` |
| `timeoutExceeded` | `TIMEOUT_EXCEEDED.test(text)` |
| `testTimeout` | `TEST_TIMEOUT.test(text)` |
| `navigationFailure` | `NAVIGATION_FAILURE.test(text)` |
| `pageException` | `PAGE_EXCEPTION.test(firstNonEmptyLine.trim())` |

where `firstNonEmptyLine = text.split('\n').find((l) => l.trim() !== '') ?? ''`.

### 5. Implement `classifyErrorText`

```ts
export function classifyErrorText(errorText: string): ErrorClassification;
```
Pure and synchronous. Steps:

1. `const text = stripAnsi(errorText);`
2. `const selector = extractSelector(text);`
3. `const signals = collectErrorSignals(text);`
4. Determine `(classification, rule)` by this **ordered if-chain — first match wins**. The
   order is exactly `CLASSIFICATION_RULE_ORDER`:

| # | rule id | condition | classification |
| --- | --- | --- | --- |
| 1 | `strict-mode-violation` | `signals.strictModeViolation` | `selector-drift` |
| 2 | `no-error-output` | `text.trim() === ''` | `other` |
| 3 | `navigation-failure` | `signals.navigationFailure` | `other` |
| 4 | `page-exception` | `signals.pageException` | `other` |
| 5 | `element-resolved` | `signals.locatorResolved` | `other` |
| 6 | `element-not-found` | `signals.elementNotFound` | `selector-drift` |
| 7 | `timeout-waiting-for-locator` | `signals.waitingForLocator && signals.timeoutExceeded` | `selector-drift` |
| 8 | `test-timeout` | `signals.testTimeout` | `other` |
| 9 | `unrecognized` | (fallback) | `other` |

5. **Post-check, applied after the chain:** if `classification === 'selector-drift'` and
   `selector === null`, then set `classification = 'other'` and `rule =
   'selector-not-extractable'`.
6. Return `{ classification, rule, selector, signals }`.

Why `strict-mode-violation` is first: its message contains `resolved to N elements`, which
must not be mistaken for a non-selector failure. Why `element-resolved` sits above
`element-not-found`: `locator resolved to` proves the selector matched something, which is
decisive (see Q4). Do not reorder to make a test pass — if the real fixture disagrees with
this order, report it as a deviation with the evidence.

### 6. Implement `classifyFailures`

```ts
export function classifyFailures(report: unknown): ClassificationReport;
```
Never throws. Implementation:

1. Cast once to a local all-optional shape:
   `const raw = (report ?? {}) as RawJsonReport;` (see **Interfaces / types** for
   `RawJsonReport`). Do not use `any`. Do not add a runtime schema validator.
2. Compute `specDir`: `const rootDir = raw.config?.rootDir ?? '';` then
   `const specDir = rootDir === '' ? '' : basename(rootDir);` using `basename` from
   `node:path`. (`basename('/Users/x/mend/tests') === 'tests'`, so a spec's `file` of
   `login-submit.spec.ts` becomes `tests/login-submit.spec.ts` — repo-relative and
   machine-independent, which is what `run_single_test` expects.)
3. Traverse `raw.suites ?? []` depth-first with a recursive helper: for each suite, process
   its `specs ?? []` in order, then recurse into its `suites ?? []` in order. This preserves
   report order deterministically.
4. For each `spec`, for each `test` in `spec.tests ?? []`:
   - increment `totalTests`;
   - if `test.status !== 'unexpected'`, continue (skipped, expected, and flaky tests are not
     failures; `retries: 0` means flaky cannot occur);
   - increment `failedTests`;
   - take the **last** result: `const results = test.results ?? []; const result =
     results.length > 0 ? results[results.length - 1] : undefined;` (`noUncheckedIndexedAccess`
     is on — guard, do not use `!`);
   - `const fullText = result === undefined ? '' : collectErrorText(result);`
   - `const classified = classifyErrorText(fullText);`
   - build the `ClassifiedFailure`:
     - `specFile`: `specDir === '' ? (spec.file ?? '') : `${specDir}/${spec.file ?? ''}``
       (forward slash literal — do not use `path.join`, which would emit `\` on Windows);
     - `testName`: `spec.title ?? ''`;
     - `projectName`: `test.projectName ?? ''`;
     - `classification`, `rule`, `selector`, `signals` from `classified`;
     - `errorText`: `clampErrorText(fullText)` — see below.
   - push into `healQueue` if `classification === 'selector-drift'`, else into `skipped`.
5. Return `{ totalTests, failedTests, healQueue, skipped }`.

```ts
function clampErrorText(text: string): string;
```
Private. If `text.length <= MAX_ERROR_TEXT_CHARS` return it unchanged; otherwise return
`text.slice(0, 4000) + '\n…[error text truncated]…\n' + text.slice(-4000)`. This mirrors
`clampOutput` in `agent/tools/run-single-test.ts`. Clamping happens **after** classification,
never before.

### 8. Create `agent/classifier/cli/classify-failures.cli.ts`

Follow `agent/tools/cli/query-selector.cli.ts` exactly in structure (an `async function
main()` invoked at module bottom, `process.exit` with explicit codes). It contains **no
classification logic** — it only parses args, calls `classifyResultsFile`, and prints.

Arguments:
- `--results=<path>` — optional, default `test-results/results.json`.
- `--json` — optional.
- Any positional argument, or any other `--flag`: usage error.

Usage lines (exact, printed to **stderr**):
```
Usage: npx tsx agent/classifier/cli/classify-failures.cli.ts [--results=<path>] [--json]
   or: npm run --silent classify:failures -- [--results=<path>] [--json]
```

Output with `--json`: `console.log(JSON.stringify(report, null, 2))` and nothing else on
stdout.

Output without `--json` — exactly one summary line, then one line per failure in report
order (heal queue first, then skipped):
```
total=5 failed=5 heal-queue=5 skipped=0
[heal] rule=timeout-waiting-for-locator selector=#login-btn spec=tests/login-submit.spec.ts test=submitting valid credentials updates the login status
[skip] rule=element-resolved selector=#login-status spec=tests/login-submit.spec.ts test=submitting valid credentials updates the login status
```
`selector=-` when `selector` is `null`. Free text (`test=…`) is last on the line so the
prefix is trivially parseable. No banners, no colour, no emoji, no timestamps.

Exit codes:
- `0` — a report was produced (whether or not anything failed, and whether or not the heal
  queue is empty).
- `2` — CLI usage error.
- `1` — the results file could not be read or parsed.

This matches `query_selector`'s philosophy (`0` = a result was produced). It deliberately
does **not** copy `run_single_test`'s exit code `3`: the classifier is a reporter, not a
verification gate, and no shell script should ever branch on "did anything fail" from this
tool's exit status.

## Risks

- **Classifying scenario 5 as `other`.** The single most likely way this task is quietly
  ruined. See the callout at the top. If the Builder finds itself writing a rule that
  mentions checkboxes, `#remember-me`, "removed", or "unfixable", it has gone wrong — stop and
  report **Blocked / unclear**.

- **The JSON report's `errors[].message` may not carry the `Call log:` block.** All the
  signatures in `breakage/README.md` were captured from the `list` reporter, not from JSON.
  This plan mitigates it by making step 1 (capture and inspect the fixture) come *before* any
  matcher is written, and by having `collectErrorText` concatenate `errors[].message`,
  `error.message`, and `error.stack`. If none of those carry the call log, do not scrape the
  `list` reporter's stdout as a workaround — report **Blocked / unclear** with one failing
  result's raw JSON.

- **ANSI escape codes inside the JSON error messages.** If `stripAnsi` is skipped or applied
  after matching, `extractSelector` will return something like
  `[2m#login-btn[22m`, which will silently poison `run_single_test` in Task 3.2
  (the literal will not be found in the spec). Strip first, always. The acceptance criterion
  asserting the five exact selectors is what catches this.

- **Regex greediness on nested quotes.** `button:has-text("Sign In")` is the test case that
  matters. `LOCATOR_SINGLE_QUOTED` uses `[^'\\]|\\.` deliberately: it stops at the first
  unescaped single quote, so the inner double quotes survive. Do not "simplify" it to
  `locator\('(.*)'\)` (greedy, breaks on chained locators) or `locator\('(.*?)'\)` (fine here
  but silently wrong the moment an escaped quote appears).

- **Rule order tampering.** If a test fails, the tempting fix is to move a rule. Do not. The
  order encodes real reasoning: strict-mode first because its message contains
  `resolved to N elements`; `element-resolved` above `element-not-found` because a resolved
  locator is decisive. Reordering to force a green test is a review failure even if the tests
  pass.

- **`page.goto` false positive from a source snippet.** If `error.snippet` were ever included
  in `errorText`, a spec line `await page.goto('/')` could trip a naive navigation-failure
  regex and skip a real selector-drift failure. Two defences: the snippet is never read, and
  `NAVIGATION_FAILURE` requires the colon (`page\.goto:`). Keep both.

- **`basename(config.rootDir)` producing a wrong `specFile`.** Correct today
  (`testDir: './tests'`) and machine-independent, which is what lets the fixture be committed.
  If `testDir` ever becomes nested, this breaks — hence limitation (i) in the README. Do not
  "fix" it now by storing an absolute path: that would make the committed fixture
  machine-specific and the test unrunnable on another machine.

- **The `testDir: './agent'` change accidentally picking up extra files.** Playwright's
  default `testMatch` is `**/*.@(spec|test).?(c|m)[jt]s?(x)`; `.cli.ts` and `.json` do not
  match, and `agent/tools/*.ts` are not `*.spec.ts`. Verify by comparing the reported test
  count before and after, and report both numbers. If unexpected files are collected, report
  it rather than adding a `testIgnore`.

- **Fixture drift.** The fixtures are a snapshot. If a later task changes a test title, a
  selector, or the app markup, the fixture tests fail loudly — which is the desired behaviour,
  not a defect. The fix is always to re-capture with the step 1 commands, never to hand-edit
  the JSON.

- **Committing with breakage on.** Step 1 and step 14 both turn breakage on. The task must
  end with `npm run break:status` printing `pristine`. If `app-under-test/index.html` is
  already dirty at the *start* of the task, that is a **Blocked / unclear** report, not
  something to `git checkout` away.

- **Scope creep into Task 3.2.** The heal queue is the deliverable. The moment the Builder
  starts writing something that *consumes* the heal queue — a loop, a prompt, a client, an
  attempt record — it has left this task.
